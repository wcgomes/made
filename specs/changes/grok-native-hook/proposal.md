# Proposal: Native Grok status hook

## Intent
The shipped grok-made plugin runs its session-status hook as `hooks/bin/status.py`, so local Grok session follow and remote SSH-10 hook activity silently depend on a Python 3 interpreter that Made does not ship and must not install. Replacing it with a small native executable shipped per platform removes every python3 prerequisite, local and remote, and is the Grok-hook part of the goal that Made installs and runs with nothing else pre-installed.

## Scope
Active change `grok-native-hook`, user-requested with the native-binary approach chosen. It modifies realized contracts in two domains:
- `specs/grok-session-follow.md`: `Grok status hook` (full observable hook behavior made explicit and preserved; native, interpreter-free hook) and `Shipped Grok plugin install` (shipped package carries the host-target hook and no test or Python file; development runs install a build-staged copy; version governed by REL-02).
- `specs/ssh-remote-workspaces.md`: `Remote OpenCode session and cwd follow (SSH-06)` (fixed staged set goes from 11 to 10 artifacts: `status.py` and `status_test.py` removed, native hook added), `Local preservation and truthful parity evidence (SSH-09)` (python3 no longer a remote prerequisite) and `Remote Grok Build session follow and tab parity (SSH-10)` (python3-missing tier reason, installer failure reason, diagnostics state and scenario variants removed; staged package carries the remote-target hook).

Unchanged and intentionally kept: every other requirement in both specs, including the remote two-tier model, consent, idempotence, ingestion bounds, pid ownership, and the local diagnostics wording.

## Non-goals
- Any change to hook event semantics, JSONL line format, log location, Made-side ingestion, dots, explorer follow, or diagnostics wording other than removing the python3-missing state.
- New hook events, new statuses, or new line fields.
- Windows remotes, Linux musl, or local Linux arm64 (not supported targets today).
- Python used only by build, CI or test tooling (`.github/scripts/assemble-desktop-package.py`, `ci-ssh-remote.yml` harness, `crates/made-platform/tests/detach.rs`); those are not product prerequisites.
- Release installers, signing, auto-update and the plugin-manifest version policy (owned by the active change `add-release-auto-update`, REL-02).
- Wiki edits.

## Approach
Rewrite the hook as a Rust binary whose observable behavior is the Python hook's contract (same events, same status rules, same seven line fields, same log path, same bounded stdin read, always exit 0, nothing on stdout), with every `status_test.py` case ported 1:1 to Rust tests. Build it for each local client target with the desktop app and for each remote companion target alongside `made-remote`, and place the matching binary inside the `plugins/grok-made` copy that each target ships: the desktop package for local installs, the per-target companion stage set for remote installs. The repository `plugins/grok-made` becomes source only; one staging script produces the shipped package for development runs, desktop packages and companion stage sets. Remove the python3 PATH detection, the python3 gate on the remote hook tier, and the `python3-missing` diagnostics state. `design.md` is not created: the decisions below, including the conditional fallbacks, fit as short entries plus tasks without overload.

## Decision index
- **Native Rust hook over alternatives:** user-chosen. A POSIX `sh` hook cannot parse JSON robustly or run on Windows; bundling an interpreter is larger and still a runtime. A Rust binary matches the existing toolchain and target matrix.
- **Crate and name:** new workspace binary crate `crates/made-grok-hook`, executable `made-grok-status` (`made-grok-status.exe` on Windows), depending only on `serde_json` plus the platform calls needed for the parent pid; pure logic in `src/lib.rs`, process glue in `src/main.rs`.
- **Bounded stdin read:** a reader thread feeding a channel with a ~2s overall deadline, decoding the first JSON value incrementally; one mechanism for POSIX and Windows, mirroring the Python Windows path. The chunk-fed decoder stays testable without real stdin, matching the ported Windows chunk-reader test.
- **Parent pid:** `getppid` on macOS/Linux; on Windows the parent process id of the current process via the Win32 API; must equal what Python `os.getppid()` reports today. Verification task 0.3 confirms Grok starts the hook directly on each platform; when it cannot be determined the result is labeled `UNVERIFIED`, since the native hook is launched exactly as `status.py` was and the pid semantics are unchanged.
- **Timestamp:** UTC, second precision, `YYYY-MM-DDTHH:MM:SSZ`, computed without adding a date-time dependency.
- **Version:** the source `plugin.json` becomes `0.1.0`, equal to `[workspace.package].version`. The version rule belongs to REL-02 of `add-release-auto-update`, whose primary mechanism is a single bump script that keeps every bundled manifest equal to the workspace version; `stage-grok-plugin.sh` writes the workspace version into the staged `plugin.json`, which equals the source version under REL-02, so staging is consistent with that rule and this change does not restate it. The remote Grok install consent is already keyed to `APP_VERSION` (`crates/made-app/src/app.rs:735`), so no new consent behavior is introduced.
- **Leftover installs above 0.1.0 (non-normative):** no end user has installed Made, but under the rollout plan iteration releases v0.1.x are published during implementation, then all are deleted and v0.1.0 is re-released. Any machine or server that ran an iteration, or a developer machine with a hand-installed 0.1.1, keeps its grok-made and its staged companions above 0.1.0 under the realized "newer installed copy stays" rule, so it would not receive the re-released 0.1.0 package. Cleanup is manual and one-time: run `grok plugin uninstall grok-made --confirm` locally and on each remote, and remove the app-owned remote staged version directories above 0.1.0 by hand, since Made has no remote delete API (SSH-06). Made does not automate this cleanup.
- **Repository source vs shipped package:** the repository `plugins/grok-made` holds source only (`plugin.json`, `README.md`, `hooks/hooks.json`). `.github/scripts/stage-grok-plugin.sh <target> <hook-binary> <out>` copies those files plus the built hook into `<out>` with mode 755. Development and release builds both resolve `<install_root>/plugins/grok-made`, the same root the OpenCode plugin uses (`crates/made-platform/src/lib.rs`, module docs lines 29 to 32), but unlike OpenCode a development build never falls back to the repository source. For a cargo build, `<install_root>` is `target/[<triple>/]<profile>/`, so developers run the script after `cargo build` (Cargo has no stable post-build or artifact-dependency hook); desktop packaging and `stage-companion.sh` call the same script.
- **Phase 0 results (verified 2026-11-05 with grok 1.0.70):**
  - 0.1 Windows command resolution: no real Windows session was possible (no signed-in grok on any runner). Documentation (`10-hooks.md`, handler `command`) says Windows starts an `.exe`, `.cmd`, `.bat` or `.com` path itself, while an extensionless path runs through Git Bash or fails under PowerShell and cmd; nothing says `bin/made-grok-status` resolves to `bin/made-grok-status.exe`. Branch selected: the repository `hooks.json` is the POSIX form and `stage-grok-plugin.sh` generates the Windows `hooks.json` with the `.exe` command name.
  - 0.2 Install copies and keeps the mode: real grok 1.0.70 on Linux (local and `ubuntu-24.04`), `macos-15`, `macos-15-intel` and `windows-2025` (probe run 41971944131, `.github/workflows/probe-grok-phase0.yml`, since removed): `grok plugin install <dir> --trust` copies the package into `installed-plugins/<name>` (no symlinks; the registry only records the source path), and files of mode 700, 755 and 644 keep exactly that mode on Linux and both macOS targets. Fallback not selected: no local mode restore, and remote work proceeds without returning to `clarify`.
  - 0.3 Direct start: documented evidence only (`10-hooks.md`: a path command "starts it directly", no `sh -c`, on Linux and macOS; Windows starts an `.exe` path itself). The logged-pid-equals-Grok-process check could not run because no signed-in grok exists on this machine or the runners; recorded as `UNVERIFIED` for 7.3 and implementation proceeds as the task allows.
- **Windows command resolution (fallback adopted now):** verification task 0.1 decides it. If Grok on Windows resolves `bin/made-grok-status` to `bin/made-grok-status.exe`, one `hooks.json` serves every platform. If not, or if neither real grok nor documentation settles it, the repository `hooks.json` is the POSIX form and the staging script generates the Windows `hooks.json` with the `.exe` command name at staging time.
- **Executable bit (fallback adopted now):** verification task 0.2 decides it. 0.1.1 already relies on Grok preserving the mode of `bin/status.py`. If the bit is not preserved, or the result is unknown, it is treated as not preserved: the local install step restores the mode on the installed hook after `grok plugin install`, and remote handling returns to `clarify` (see conflict above).
- **Per-target packaging:** the local desktop package (`.github/workflows/ci-artifacts.yml`) stages the host-target hook, and a per-OS CI step runs it from the packaged layout with no Python on PATH and checks the recorded parent pid; the remote hook is built by `.github/scripts/build-linux-companion.sh` (inside `rust:1-bullseye`, release profile, `check-glibc-max.sh` 2.31, musl-interpreter and GUI-link checks) and `.github/scripts/build-macos-companion.sh` (minos 12.0, GUI-link check), passed to `.github/scripts/stage-companion.sh`, which records it in `manifest.json` and `SHA256SUMS`, and checked by `.github/scripts/assemble-desktop-package.py`; the remote stage (`.github/workflows/ci-ssh-remote.yml`, `made_app::remote_session::STAGE_FILES`, the `made-platform` stage script) carries the target hook built under the same glibc 2.31 / macOS 12 constraints as `made-remote`, with mode 700 enforced where `status.py` had it. The fixed staged set becomes 10 artifacts.
- **Wire compatibility:** `Capabilities.python3` stays in protocol major 1 as a frozen field, always encoded false and ignored by every consumer, mirroring `Capabilities.tmux`; the remote probe stops looking up python3.
- **Python removal:** delete `status.py` and `status_test.py`; drop the python3 gate in `crates/made-remote/src/grok.rs`, detection in `crates/made-remote/src/{main,supervisor}.rs`, the probe lookup in `crates/made-platform/src/ssh.rs`, the probe parse in `crates/made-app/src/ssh_servers.rs`, and the `python3-missing` reason and `REMOTE_PYTHON3_MISSING` row in `crates/made-app/src/{diagnostics,app,ui,workbench}.rs`.
- **Tests:** every `status_test.py` case is ported 1:1 to Rust tests in `crates/made-grok-hook`; the shipped package contains no test file. The staging-script test is Unix-only so no Rust test needs bash on Windows; Windows staging is covered by the packaged-layout CI step.
- **Landing order:** tasks 2.6 through 6.3 land in a single merge to main, so no development, desktop or remote package ever references a hook file it does not contain; the hooks.json switch and the Python deletions (phase 6) come after the packaging tasks in phase 5.
- **Accepted differences from the Python hook (non-normative):** the native decoder decodes the accumulated buffer, so a valid multibyte UTF-8 character split across two reads is kept intact where Python produced replacement characters; only genuinely invalid bytes become replacement characters, as spec.md requires. Each line is appended with a single write; the no-interleaving guarantee covers local filesystems, and a `GROK_HOME` on NFS or another network filesystem is not guaranteed. Numeric zero (`0`, `0.0`) is falsy for `stopHookActive`, as in Python.
- **Existing wording kept:** the realized `Turn end and session end` scenario says a failure is attention; the hook writes status `error`, which the dots render as attention. The wording is left unchanged.
- **No design.md:** overflow rule not met.

## Clarifications
- **Q:** What exact grok-made version ships?
  **A:** `0.1.0`, equal to the workspace version. The "above 0.1.1" requirement and the 0.1.1-upgrade scenarios are dropped. Version policy is REL-02's; staging writes the workspace version, equal to the source under REL-02. Iteration releases v0.1.x published during implementation are deleted before v0.1.0 is re-released. Machines and servers that ran an iteration, and hand-installed 0.1.1 developer copies, are cleaned up once by hand: `grok plugin uninstall grok-made --confirm` locally and on each remote, plus removal of the remote staged version directories (see the decision index).
- **Q:** Must `status_test.py` coverage be ported 1:1, and does the package keep a test file?
  **A:** Port every case 1:1 to native Rust tests; ship no test file in the plugin package.
- **Q:** In a development run, what is the shipped package?
  **A:** The repository `plugins/grok-made` holds source only; the build stages a copy under `target/` with the built hook, that staged copy is the shipped package in development runs, and the README manual install points to the staged path. Analyze refinement: the staged copy sits at `<install_root>/plugins/grok-made`, which for a cargo build is under `target/`, resolved like the OpenCode plugin but without a repository fallback.
- **Q:** Does SSH-06's fixed count of 11 staged artifacts change?
  **A:** Yes; a MODIFIED SSH-06 entry records 10 artifacts (`status.py` and `status_test.py` removed, hook executable added), otherwise copied unchanged.
- **Q:** How does Grok on Windows resolve the hook command, and does `grok plugin install` preserve the executable bit?
  **A:** These are facts to verify, not user decisions. Early verification tasks use real grok when a runner has it, otherwise documented evidence. Fallbacks are adopted now: per-platform `hooks.json` generated at staging if `bin/<name>` does not resolve `<name>.exe`, and the install step restores the mode if the bit is not preserved. spec.md stays outcome-only: the hook runs on every supported platform.
