# Proposal: Grok session follow

## Intent

Made already follows an OpenCode session inside a terminal tab. The same workspace should follow a Grok Build session's directory and show that session's status on the workspace tab, using the behavior validated in the proof of concept. When Grok is installed it should appear in the `+` menu the same way OpenCode does, and that detect, list, and launch behavior is the catalog behavior for every integrated TUI. The interactive Grok TUI cannot load a plugin for one launch, so Made itself installs the shipped status plugin after PATH detection reports grok.

## Scope

Observable Grok directory follow and workspace-tab status dots for sessions open in that tab. After PATH detection reports grok, Made installs the shipped `plugins/grok-made` plugin with `grok plugin install <absolute shipped path> --trust`. The `+` menu is where OpenCode and Grok are offered, from one integrated-TUI catalog, and other agents are not. Affects the OpenCode session-follow contract where it currently forbids any agent except OpenCode, and the shell-versus-agent root precedence. Workspace-tab dots reuse the existing OpenCode dot treatment. The OpenCode row keeps its current launch. Revealed About diagnostics show one Grok Build row directly with the existing OpenCode status pill. That row stays per workspace, hidden until Show diagnostics, and out of the normal workspace chrome. After the shipped plugin install succeeds or the installed version is already current, that workspace's row is ready only while Grok is running there. The OpenCode diagnostics row uses that same wording pattern: inactive `OpenCode is not running.`, ready `OpenCode session follow is ready.` including after a reconnect, and `OpenCode is not on PATH.`

## Non-goals

Claude Code, Codex, and any other agent TUI. OSC 7501. ACP `session/list` or `x.ai/sessions/list` as the status source. A Grok session map. Focusing or switching a Grok session from Made. Hand-editing the user's Grok config.toml. Installing the plugin through `GROK_CONFIG`, `--plugin-dir`, or OpenCode's plugin environment. Changing the OpenCode row's launch behavior, follow, or dots. Changing OpenCode reason sentences other than the not-running, ready, reconnect, and not-on-PATH sentences. The shared `+` menu may gain catalog rows.

## Approach

Keep two sources. `active_sessions.json` is the inventory of sessions still open in the terminal's Grok process. The app-owned `plugins/grok-made` hook appends one status line per session event, and Made applies only lines written after it starts. The inventory refreshes about once a second and moves the explorer when a newly attached session appears. The hook moves the explorer immediately when that session starts or receives a prompt, and it sets the dot. OpenCode, when connected, keeps the root and the dots.

The `+` menu is catalog-driven. Detection stays a metadata-only PATH lookup on the existing background thread: it never spawns the program, never checks a version, never installs a plugin, ignores empty and relative PATH segments, and must not delay shell or explorer startup. After that lookup reports grok, separate background work ensures the shipped plugin is installed with `grok plugin install <absolute shipped path> --trust`. That work must not block shell, explorer, or Grok startup. With no detected integrated TUI, `+` opens the folder picker and shows no menu. Otherwise the menu is Terminal first, then one row per detected integrated TUI in catalog order. PATH detection, the shipped-plugin install, and an explicit catalog that did not run detection drive one Grok Build row in the revealed About diagnostics. Once that install has succeeded or the installed version is already current, the row for a workspace is ready only while Grok is running in that workspace, and inactive with `Grok Build is not running.` when it is not. The other Grok row sentences stay as they are. The OpenCode diagnostics row uses the same pattern for not running, ready, and not on PATH. Its other reason sentences stay. The row does not block the UI, and copying the diagnostics report includes its sentence.

## Decision index

- **Two sources:** the JSON inventory lists open sessions and directories; the hook supplies immediate path updates and the only status. Neither source alone is the product.
- **Plugin install:** After PATH detection reports grok, separate background work ensures the shipped `plugins/grok-made` (beside `plugins/opencode-made`, in the development repository or the install-root copy) is installed with `grok plugin install <absolute shipped path> --trust`. The `plugin.json` `version` is compared as a dotted numeric version: the same version skips install, a missing or older copy is installed by that command, and a newer installed copy stays. The PATH lookup itself does not install. A catalog supplied without that lookup does not install. Install failure still lets the user start Grok, and Made records for Grok session follow that session-status hooks are unavailable. Interactive Grok cannot load the plugin for one launch, `GROK_CONFIG` cannot add plugins or hooks, and `--plugin-dir` applies to `grok agent` rather than `grok dashboard`, so Made does not use OpenCode-style injection and does not hand-edit `config.toml`. Removal stays `grok plugin uninstall grok-made --confirm`.
- **Ask is attention:** `ask_user_question` is the yellow dot. A permission notification is the same dot. Answering the question returns the dot to working.
- **No yank:** a one-second inventory refresh must not move the explorer back to a session that is merely the newest attachment after the user has prompted a different open session.
- **Focus limit:** selecting an already-open session, with no new attach and no new prompt, does not move the explorer. Accepted.
- **OpenCode first:** a connected OpenCode session owns the explorer root and the workspace-tab dots. This is follow precedence, not menu order.
- **Catalog order:** OpenCode, then Grok. Omit whichever is not on PATH. If only Grok is installed, the menu is Terminal, then Grok.
- **Detection:** metadata-only PATH lookup on the existing background thread. It never spawns the program, never checks a version, never installs a plugin, ignores empty and relative PATH segments, and must not delay shell or explorer startup. Made never auto-launches a TUI.
- **Grok row:** the label is Grok Build. The 16px leading slot paints the official mark in `grok.svg`: the two paths from https://grok.com/images/favicon.svg, fill #FCFCFC, viewBox "56 56 400 400". Do not redraw the mark. While OpenCode is not active, an open Grok tab — a running Grok TUI, even before a session, or a shell tab with open Grok sessions — uses that same label and mark. The tooltip is the session summary when sessions exist and omits the workspace path. When Grok is not open, the tab uses the folder label and the terminal glyph. OpenCode, when active, keeps its label, icon, and dots.
- **Grok launch:** choosing Grok starts that executable's absolute path plus the argument `dashboard` directly as the child of a new home-directory tab, with no shell first and no picker, and the current tab keeps running. That launch does not inject plugin configuration and does not write the user's Grok config. Typing `grok` in a shell stays valid and is not given that argument.
- **OpenCode row:** the shared menu may gain catalog rows. The OpenCode row keeps its vendored 16px `opencode.svg` and its existing launch behavior, including launch injection, follow, and dots. Its diagnostics row uses the Grok wording pattern. While session follow is not connected and no other OpenCode reason applies, the pill stays inactive and the sentence is `OpenCode is not running.` While connected, including after a reconnect, the visible pill is `ready` in the success tone and the sentence is `OpenCode session follow is ready.` The machine-readable status code may stay `connected`. When OpenCode is not on PATH, the sentence is `OpenCode is not on PATH.` and the pill keeps the existing degraded or unsupported treatment. Other OpenCode reason sentences stay. Grok sentences stay. This withdraws the requirement that the inactive sentence stay `Optional OpenCode integration is inactive.`
- **Grok diagnostics row:** Revealed About diagnostics show exactly one Grok Build row directly with the existing OpenCode status pill, using that pill-plus-sentence treatment. It is per workspace, stays hidden until Show diagnostics, and is absent from the normal workspace chrome. The realized UI spec still describes the existing OpenCode pill; this delta adds the Grok row beside it and does not replace that pill. While PATH detection is still running, the pill is inactive and the sentence is `Checking for Grok Build.` That in-progress lookup is not shown as not on PATH. When detection has finished and grok is not on PATH, or an explicit catalog omits Grok and detection is not running, the pill is inactive and the sentence is `Grok Build is not on PATH.` When grok was detected and the shipped-plugin install is still running, the pill is inactive and the sentence is `Installing the Grok Build plugin.` Still running lasts until the install succeeds, the installed version is already current, or the install fails. Already current means the installed version is equal to or newer than the shipped version. Success or already current uses pill ready in the success tone and `Grok Build session follow is ready.` only while Grok is running in that workspace. Running means either that workspace's terminal target is Grok and that process is still alive, or that workspace's shell has at least one open Grok session. OpenCode owning the tab label does not by itself hide a running Grok. Grok running only in another workspace does not make this row ready. When that install is in place and Grok is not running in that workspace, the pill is inactive and the sentence is `Grok Build is not running.` Checking, not on PATH, installing, hooks unavailable, and the explicit-catalog sentence stay unchanged. Install failure uses pill degraded and `Grok Build session-status hooks are unavailable.` An explicit catalog that includes Grok but did not run PATH detection uses pill inactive and `Grok Build plugin was not installed for this launch.` and does not claim ready or that an install is running. The copied diagnostics report includes the same Grok sentence.

## Clarifications

- **Q:** Should merely focusing an already-open Grok session move the explorer?
  **A:** No. Neither validated source updates on focus alone. Recorded as an accepted limit.
- **Q:** What does the Grok row in the `+` menu show, and should Made invent a Grok logo?
  **A:** The label is Grok Build. Its 16px leading slot paints the official mark in `grok.svg`, the two paths from https://grok.com/images/favicon.svg, fill #FCFCFC, viewBox "56 56 400 400", with no squircle, filter, foreignObject, or blur. That file is not in the vendored Material icons. An open Grok tab uses that same label and mark. When Grok is not open, the tab uses the folder label and the terminal glyph.
- **Q:** When the shipped plugin is installed or already current, is the Grok diagnostics pill always ready?
  **A:** No. It is ready only while Grok is running in that workspace. Running means either the workspace terminal target is Grok and that process is still alive, or the workspace shell has at least one open Grok session. OpenCode owning the tab label does not by itself hide a running Grok. When that install is in place and Grok is not running in this workspace, the pill is inactive and the sentence is `Grok Build is not running.`
