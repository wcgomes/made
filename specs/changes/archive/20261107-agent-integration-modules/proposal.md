# Proposal: Agent integration modules

## Intent
Made's three agent integrations (OpenCode, Grok Build, Claude Code) are spread over six parallel representations of the integration set and dozens of per-integration matches, boolean flags and hard-coded precedence chains in the core, so every change to one integration touches shared code and every new integration edits all of it. This change reorganizes the code, without changing behavior, so that each integration is one module of a standard structure implementing one common interface, referenced from one static list that the core iterates. It is a code-organization refactor to ease maintenance, reduce the risk of changes and make adding an integration a matter of creating a new standard module and referencing it; it is not a dynamic or plugin system.

## Scope
Active change `agent-integration-modules`, user-requested. It adds one new domain and modifies none:
- New `specs/agent-integration-architecture.md` (created on archive): behavior preservation across all integration surfaces (AIA-01), the standard integration structure (AIA-02), the single static integration list (AIA-03), extension without core edits verified by a test-only fake integration (AIA-04), declared precedence (AIA-05), declared per-integration follow policy that keeps today's divergent semantics (AIA-06), declared launch arguments and environment policy (AIA-07), declared diagnostics contribution with preserved literals (AIA-08), set-pinning tests that derive from the list and keep explicit pins (AIA-09), a shared library for the two native hooks with byte-identical output (AIA-10), and incremental delivery with green CI after each step (AIA-11).
- Local integration seams in `made-app` and `made-platform` (catalog and detection, launch arguments and environment, per-app and per-tab runtime state, polling, explorer follow and precedence, tab branding, dots and tooltip, diagnostics rows, About rows, copied report, smoke markers, scope declaration), the two hook crates, and the tests that pin the integration set.
- Remote and SSH code is excluded from the core-neutrality rule (AIA-02): `ssh_servers.rs`, `remote_workspace.rs`, `remote_session.rs` and delimited remote paths in core files may use an integration module's typed helpers; their logic does not change.
- End-of-work wiki updates: `wiki/architecture.md` (rule 4, module table, hook-crate dependency columns), `wiki/runtime/terminal-first.md`, a new `wiki/integration/adding-an-integration.md` page with its `wiki/integration/index.md` link, and a new ADR `wiki/decisions/0009-static-integration-modules.md` with its `wiki/decisions/index.md` entry.
- In-scope renames of misleading names, with no behavior change: `push_grok_diagnostics` (also pushes Claude Code), the `ClaudeDiagnosticsPill` alias of `GrokDiagnosticsPill` (one neutral pill type), `grok_status_pill_ui` (also paints the Claude Code row), and `opencode_sessions_summary` (generic despite its name).

No MODIFIED or REMOVED block is needed: no realized spec or active delta text names the internal structure this change reorganizes (checked: `specs/*.md` and the `spec.md` of `claude-code-integration`, `grok-native-hook` and `add-release-auto-update`; internal names such as `CompatibleTui`, `RootSource`, `V1_SCOPE`, `AgentIntegration` and the hook crate names appear only in their proposals, designs and tasks, which are non-normative).

## Non-goals
- Any observable behavior change for users, including fixing pre-existing inconsistencies between integrations (they are preserved and declared, see AIA-06).
- A plugin system of any kind: runtime registry, discovery, dynamic loading (dylib, WASM, scripting), external manifests, or configuration- or environment-driven selection of integrations.
- Remote/SSH generalization: `LaunchTarget` agent generalization, a generic remote operation set, the frozen companion `Capabilities`, remote `RootSource` and `candidate()`, the remote `TerminalTarget` variants, remote `+` menu items, `ssh_servers.rs` consent and install, remote diagnostics producers and remote Claude Code detection through `made_remote::grok::detect_on_path`. Deferred to a later change because it is higher risk and touches the client/companion wire protocol.
- Single-sourcing of the remote staging lists (`remote_session::STAGE_FILES`, the `made-platform` staging script, `made-remote` `ARTIFACTS`/`GROK_ARTIFACTS`, CI scripts). Excluded, see the decision index.
- Adding a new agent integration to the product; the product list stays OpenCode, Grok Build, Claude Code (V1 Scope Boundary).
- The pre-existing Windows warnings in `crates/made-platform/src/detach.rs` (unused imports and constants behind `cfg(unix)`-only callers, identical on `origin/main`); a separate small fix.
- Moving channel code that is inherently integration-specific out of its crate: `made-bridge`, the OSC 7501 scanner in `made-terminal`, plugin packages under `plugins/`, OpenCode paths and version probe in `made-platform`.
- Wiki edits during this change's spec work (end-of-work wiki tasks are planned in `tasks.md`).

## Approach
Each integration becomes a module under `crates/made-app/src/integrations/<name>/` that declares its data (identifiers, labels, program, mark, precedence rank) in a const descriptor and its behavior through one compile-time trait (launch arguments and environment policy, detection reaction, app-wide and per-tab runtime state, polling, follow channel and policy, presentation, diagnostics contribution). One static slice of trait-object references, in catalog order, is the only place the product names its integrations; the core takes that list (or an injected list of the same type in tests) and iterates it at every seam instead of matching on integrations. Per-integration runtime state is held per workbench and per app in slots parallel to the list, and only the owning module touches its concrete state. Precedence is a declared rank, not list order, so catalog order and precedence stay independent. Today's divergent follow semantics are encoded as declared policy and pinned by characterization tests written before any code moves. Integration identity in `made-platform` stops being a closed enum: detection becomes generic over program names and per-integration plugin-directory fields become one generic accessor. The two native hooks share identical code through a new library crate `made-hook-common`; each keeps its own binary, mapping and output. Delivery is four independently mergeable steps plus a final rename and docs PR: interface, list and every integration as a state-owning module plus Claude Code's channel code, then Grok Build's channel code, then OpenCode's channel code with shim removal, then the hook library. `design.md` holds the interface sketch, the module layout, the seam inventory, the follow-policy table, the migration and the alternatives, because they do not fit as short decision entries.

## Decision index
- **Static trait-object list over alternatives:** a `&'static [&'static dyn Integration]` in catalog order, with const descriptors for data and trait methods for behavior. Rejected: dynamic plugins (dylib, WASM, scripting) and manifest- or config-driven integrations (user non-goal; adds loading, versioning and security surface for no need); a closed enum with match or `enum_dispatch` (every addition edits the enum and its matches, and a test-only fake cannot add a variant without production edits, so AIA-04 could not be verified); a data-only descriptor table (behavior differences such as follow policy and launch preparation would stay as matches in the core); a compile-time generic type list (heavy generics in `Workbench` and `AppModel` for no benefit at three entries). See [design.md](design.md#approach).
- **Identity is the list entry, not an enum:** `CompatibleTui` and `AgentIntegration` are replaced by an `IntegrationRef` compared by its descriptor key; `TerminalTarget::Tui` carries it. `made-platform` detection becomes generic over program names; `V1_SCOPE` is derived from the list. Every legacy identifier string is a descriptor field and keeps its value (menu ids `opencode`/`grok`/`claude`, scope ids `opencode-v2`/`grok-build`/`claude-code`, root sources `opencode`/`grok`/`claude-code`). See [design.md](design.md#identity-and-descriptor).
- **No `CompatibleTui` shim and no lint suppression:** the identity group migrates every caller at once (variants become `OPENCODE`, `GROK`, `CLAUDE_CODE`; `ALL` becomes `PRODUCT` with the same order). Transitional code is only public accessors and `pub use` re-exports inside `transitional-shim (AIA-11)` markers, which trigger no lint, are exempt from neutrality scans and are removed in step 3; no `#[allow]` is added anywhere.
- **Rank, not order:** precedence is a declared rank with gaps (OpenCode 100, Claude Code 200, Grok Build 300; lower wins), independent of catalog order, unique by test. See [design.md](design.md#precedence).
- **Two follow kinds:** the bridge "session channel" (OpenCode: active session, view directory, epochs; exactly one owner, which is what `is_agent_owned` means today) and ranked "directory follow" (Claude Code, Grok Build, and any new integration), each with a declared policy for unusable directories and for reports while outranked. A second session-channel owner is outside the extension guarantee. See [design.md](design.md#follow-policy).
- **Divergent follow semantics are declared, not unified:** Claude Code rejects unusable directories and retains while OpenCode holds; Grok Build is silent on unusable directories, ignores reports while OpenCode holds and retains while Claude Code holds. Pinned by a branch-table characterization test before any move. See [design.md](design.md#follow-policy).
- **Launch environment is declared per integration:** each integration declares which local targets receive its variables (the shell target, its own direct target) and which variables are stripped elsewhere; the core composes the tab environment from declarations (applied last entry first, see the env-order decision), keeping the current prepare-before-spawn and after-spawn ordering and log lines. See [design.md](design.md#launch).
- **Per-tab and app-wide state in slots:** `Workbench` and `AppModel` hold one optional boxed state per list entry; only the owning module downcasts to its concrete type. Polls return reports (directory, presentation) to the core instead of mutating the coordinator, which avoids borrow conflicts. See [design.md](design.md#runtime-state).
- **Interface is `pub` but not a plugin API:** the trait is public in `made-app` so the external test crate can define the fake integration; it is compile-time only and documented as such. The constructors that accept an injected list (`AppModel::with_integrations`, `SessionFollowCoordinator::with_integrations`, the menu model builder, the diagnostics rows builder, the tab-info and About-row UI helpers) are `#[doc(hidden)]` test support, reachable only from code, never from configuration (AIA-03).
- **`V1_SCOPE` stays a const:** `PRODUCT` is a `const` slice, so `V1_SCOPE` keeps its boolean fields and `const` asserts unchanged and defines `agent_integrations: PRODUCT`; readers of `id()`/`name()` adapt to the descriptor's `scope_id`/`scope_name`. See [design.md](design.md#identity-and-descriptor).
- **Fake integration covers every seam:** at two ranks (250, between Claude Code and Grok Build, and 150, between OpenCode and Claude Code), across menu, detection reaction, launch, state slots, polling and teardown, follow, presentation, diagnostics, About, report and smoke marker; committed list-variation tests (product list, product plus fake, product without Claude Code) replace any manual mutation check (AIA-04).
- **Tests adapt only paths:** existing tests may change imports, accessors and constructors for moved code, and source scans may add scanned files; expected values do not change; set-asserting tests derive from the list and explicit pins remain (AIA-01, AIA-09). Old public paths keep `pub use` shims until the last `made-app` step, which removes them in a path-only commit.
- **Characterization tests first:** step 1 begins with tests written against today's code for the follow branch table, the launch-environment matrix, the copied report, smoke markers, tab branding by precedence and diagnostics rows; they protect all later steps. Each drives behavior through one delimited test-only adapter block, so after an API change only that block changes and no expected value does.
- **Adapters own their state (option a, coordinator decision):** in step 1 all three integrations become modules whose structs own their current per-tab and app-wide state, moved wholesale from `Workbench` and `AppModel` with logic unchanged, and the core iterates the list at every seam. State moves in an additive skeleton group followed by one small atomic group per integration (Claude Code, Grok, OpenCode), each starting with an inventory of reader files and adding transitional accessors for them; steps 2 and 3 only relocate the remaining Grok and OpenCode channel-logic files and remove shims, so no seam ever has a half-generic chain. See [design.md](design.md#migration-and-rollback).
- **Migration order:** (1) characterization baselines, then 1a interface, list and generic identity with all three integrations as state-owning modules and the fake integration, then 1b Claude Code channel code; (2) Grok Build channel code; (3) OpenCode channel code and shim removal; (4) `made-hook-common`; then a final small PR with the remaining scoped renames, the wiki updates and ADR 0009. Each step is one mergeable PR with green CI and no persisted data, so rollback is a revert. Step 4 has no code dependency on steps 1 to 3 but follows the requested order.
- **Shared hook library:** new crate `made-hook-common` (library only) with the identical parts: `Chunk`, `READ_DEADLINE`/`POLL_SLICE`, `spawn_stdin_reader`, `format_timestamp`, `json_string`, `field_text`, `text_of`, the panic-silent `main` wrapper and the Windows Toolhelp parent lookup. Diverged `read_event_with` (Claude Code adds the 8 MiB `MAX_INPUT` cap and the `}` gate) moves only as a parameterized function if both hooks' existing tests and the golden corpus pass unchanged; otherwise each hook keeps its own. Hook crates re-export moved public items so their tests keep their paths. See [design.md](design.md#shared-hook-library).
- **Staging-list single-sourcing excluded:** the staged set is part of the client/companion contract (SSH-06 counts its artifacts, `manifest.json` and `SHA256SUMS` list it), spans three crates and Python and shell CI scripts that cannot share a Rust constant, and changes only with remote integration work, which is deferred. Single-sourcing it belongs with the remote generalization change.
- **Exceptions to "no core edits":** the central secret-redaction key list (`is_sensitive_env_key`) stays central as a security review point and needs an edit only if a new integration's variable carries a secret not matched by its generic patterns; remote/SSH code, packaging and CI scripts, and spec contract changes are outside the guarantee (AIA-04).
- **Naming cleanup:** one neutral pill type replaces `GrokDiagnosticsPill` and the `ClaudeDiagnosticsPill` alias; `push_grok_diagnostics`, `grok_status_pill_ui` and `opencode_sessions_summary` get neutral names; `claude_follow` stops importing `grok_follow::process_belongs_to_with`, which moves to a shared process-ancestry module.
- **ADR 0009:** `wiki/decisions/0009-static-integration-modules.md` records the static trait-object list, ranks, declared follow policy, compile-time only (not a plugin system) and the AIA-04 exceptions including remote; linked from the new adding-an-integration page.
- **Env contribution order declared:** contributions apply from the last list entry to the first, so the earliest entry wins on a shared variable; pinned by `contributions_apply_last_entry_first_so_the_earliest_entry_wins` (design.md launch flow).
- **Dynamic-loading scope narrowed:** AIA-03 forbids dynamic loading only as a direct dependency of any workspace crate; transitive platform or graphics dependencies (for example `libloading` through the graphics stack) are out of scope.
- **design.md created:** overflow rule met (interface and module design, seam inventory, follow-policy table, migration order, alternatives).

Decisions settled by the characterization tests (today's behavior, kept by the refactor):
- The two hooks diverge on reading: the Grok Build hook has no input cap and no completion gate (a 9 MiB object and an object followed by text are read at once, a syntax error ends the read at once); the Claude Code hook refuses more than 8 MiB, parses only a buffer whose last non-whitespace byte is `}`, so text without a closing brace is waited on until the 2 second deadline.
- The dot of a Grok session that is only attached (inventory row, no hook line) is idle; the tab precedence is OpenCode, then Claude Code, then Grok Build, whichever of Claude Code and Grok Build arrives first.
