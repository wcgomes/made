# Proposal: SSH workspaces with local-experience parity

## Intent
An SSH terminal alone does not satisfy the requested outcome. A remote workspace must provide the existing Made experience against the selected server: explorer, safe preview and live updates, read-only Git, terminal, OpenCode session integration and directory follow, with independent tabs and honest connection failures.

## Scope
Add SSH server registration, connection testing and remote OpenCode and grok detection through a `Servidores SSH` action beside Hide/Show Explorer; add `Terminal SSH` and, when detected, `OpenCode SSH` and `Grok SSH` to `+`. Extend workspace identity, remote filesystem access, Git observation, terminal lifecycle, optional integration, diagnostics and isolation without regressing local workspaces, and extend the same optional integration to remote Grok Build session follow with a consent-gated official plugin install (SSH-10). The delta affects the domains realized in `specs/opencode-session-follow.md`, `specs/made-ui-ux.md`, `specs/grok-session-follow.md` and `specs/explorer-file-icons.md`.

## Non-goals
Archive disposition: before moving this change folder, the scoped implementation archive MUST reconcile and merge the ADDED requirements into new `specs/ssh-remote-workspaces.md`, replace the MODIFIED Security and Local-Only Integration requirement in `specs/opencode-session-follow.md`, and replace the MODIFIED Minimal Workspace Layout requirement in `specs/made-ui-ux.md`; there are no REMOVED requirements and no overlapping active deltas. No remote editor/save, Git writes or worktree management: these are not local Made capabilities. No silent remote installation, wildcard bridge listener, copied SSH private key, disabled host verification, persistent personal configuration edits, general file synchronization or remote Windows support. No remote tab/session recovery across client restart or server reboot; server metadata persists, live session credentials do not. No tmux dependency, probe, configuration, fallback or installation, and no authorization to install tmux or a Rust toolchain on a remote or in a development container. No unconsented write into the remote user's Grok home, no `GROK_HOME` redirection, and no separate `ssh-remote-grok-build` change: the user directed this open change to absorb the approved Grok parity work.

## Approach
Keep the existing native UI and per-tab ownership; introduce an explicit execution/filesystem authority rather than interpreting server paths as host paths. Reuse terminal rendering, tree/preview presentation, session precedence and Git presentation behind authority-aware operations. Use host OpenSSH and an explicitly consented, versioned private remote companion/plugin. An app-owned supervisor, detached through made-platform OS process capabilities, owns that tab's PTY, filesystem watchers, bounded VT state and the remote loopback integration bridge. SSH stdio relays bounded events/operations, not an externally exposed bridge. User-installed tmux is irrelevant. See [design.md](design.md) for alternatives and concrete interfaces.

The user answered **“Pode implementar”** to the six explicit recommendations relayed below, and later approved the recorded OpenCode tab-parity and remote Grok Build expansion of this same change. This authorizes those outcomes, not a claim that they already work. Clarify is complete, the executable plan is in [tasks.md](tasks.md), and the analyze results are recorded there. That preparation record is historical at proposal time; implementation is complete for 105 of 108 executable tasks and the current state is archive preparation, with only 3.9, 5.3 and 5.4 remaining `UNVERIFIED` accepted limits.

- **Confirmed — update the existing companion on a same-version mismatch:** when an existing same-version app-owned companion/plugin set has missing, corrupt or different bytes, Made MUST update that existing target instead of retaining additional content-addressed or per-build companion directories. Refusal or cancellation performs no remote write or delete, and a generic `ssh connection failed` or an app-version bump is not an acceptable outcome. An approved fixed-script update writes all 11 artifacts to a private temporary sibling, verifies sizes, hashes and permissions, swaps the existing path atomically or rollback-safely, and removes temporary/replaced owned directories so builds do not accumulate; any pre-swap failure leaves the original untouched and preserves actionable failure detail. Companion and Grok-install launches keep resolving the same version/target path, running companions/terminals keep their OS lifecycle, and reattach/protocol major 1 are unchanged. A pre-attach stage/open failure surfaces a bounded Explorer unavailable/failure state rather than perpetual `Loading folder…`, with no companion spawn and no extra routine SSH chrome. See [update decision](design.md#same-version-companion-update-after-the-user-correction).

  **A:** No. The user explicitly requires the remote explorer and the whole existing local experience, including remote files/live preview/Git, terminal/OpenCode, session and cwd follow, independent tabs and disconnection handling (confirmation relayed by the coordinator).
- **Q:** Where are SSH actions exposed?
  **A:** `Servidores SSH` beside Hide/Show Explorer manages registration, testing and OpenCode detection; `+` offers `Terminal SSH` and `OpenCode SSH` when remote OpenCode is detected (confirmation relayed by the coordinator).

### Resolved Q1–Q6 (approval relayed by coordinator)
The user's single response “Pode implementar” approved the explicit package below. The following are the approved recommendations, not six separately invented answers.
1. **Q1 — approved:** persist server metadata only, without credentials. Technical detail: add/edit/remove app-owned records; removing/editing a record affects future launches, not the authority of an existing tab; do not restore live tabs across restart.
2. **Q2 — approved:** reuse OpenSSH, keys/agent and password/MFA prompts; unknown hosts require explicit approval. Technical detail: honor existing SSH aliases/ProxyJump, use app-owned trust additions, reject changed keys, never forward agents or persist prompt answers; no separate jump-host editor is added.
3. **Q3 — approved:** private remote Made helper/plugin with consent, without altering personal configurations or installing OpenCode. Technical detail: packaged verified artifacts, per-version/server consent for initial staging and exact reuse, a separate per-attempt `Update companion` approval for same-version mismatches, update-in-place with verified swap and cleanup instead of retained build directories, and an explicit failure/cancel path. The earlier tmux-prerequisite sentence is superseded by the correction below; absence of tmux is not a failure and is not an installation prompt.
4. **Q4 — approved:** Linux/macOS remotes initially; Windows remotes excluded. Technical detail: the exact architecture/prerequisite matrix and bounded controlled-network budgets in spec.md are engineering acceptance defaults, not claims that every Linux/macOS variant already works.
5. **Q5 — approved:** image upload only through explicit paste, remote temp storage with defined cleanup, no clipboard synchronization. Technical detail: both remote image chords use the approved upload-and-server-path mechanism and disclose that behavior; local default/native versus fallback semantics stay unchanged. A remote path attachment is not represented as native clipboard access.
6. **Q6 — approved:** preserve terminal/OpenCode during network interruption and reattach without replay of commands/input. Technical detail: app-owned detached supervisor, 24-hour detached lease, exclusive attach/epoch, complete modes/mouse/alternate-screen resnapshot without historical replay, explicit expiry/host-failure limits, local release independent of unreachable remote cleanup and no automatic process replacement. Details are normative in spec.md.

- **Q:** Must Made depend on, probe, or install tmux so a remote terminal can survive and reattach?
  **A:** No. After the package approval, the user corrected the mechanism: Made must not depend on tmux; if the user wants tmux, they install it themselves. tmux is irrelevant to Made — not a prerequisite, fallback, probe, configuration target or hidden requirement. This correction does not authorize installing tmux or a Rust toolchain on the inspected or any other development container. Q6's survival and no-replay outcome remains; the owner is the native supervisor described above.

- **Q:** How does the client know the resnapshot has ended without a new snapshot verb?
  **A:** Independent review found that split `TerminalOutput` frames have no end, so an empty poll can reopen input too early or leave an active session closed. The correction stays inside the approved no-replay outcome: the existing verb gains a required `done` bit. That is not a new operation, not a protocol-major change, and not a return to tmux.

- **Q:** Should the remote OpenCode tab-parity defect and full remote Grok parity be fixed in this change or a new `ssh-remote-grok-build` change?
  **A:** The user directed updating this open `ssh-remote-workspaces` change in place, superseding the earlier recommendation to create a separate Grok change; no new change folder is authorized.
- **Q:** How closely must remote match local for these flows?
  **A:** The user requires remote and local UX/features to match for the covered OpenCode and Grok flows: exact tab label/icon/dots presentation, session/cwd follow behavior, open/close lifecycle and honest integration diagnostics, with disconnect/exit clearing stale activity.
- **Q:** How is full remote Grok activity authorized?
  **A:** Made runs the official `grok plugin install <staged-plugin> --trust`, persistently installing the shipped plugin in the remote user's existing Grok home, only through a separate explicit per-server/version consent. Hook activity requires an installed grok-made equal to or newer than the shipped one: the consented install or a user's own pre-existing install can supply it, and in the latter case Made performs no Grok-home write and needs no consent. Without any installed plugin equal to or newer than the shipped one, the Grok-native `active_sessions.json` inventory still provides owned sessions, cwd follow, lifecycle and running indication, and hook-driven activity/status and prompt-event timing stay honestly unavailable. `GROK_HOME` redirection is prohibited, the official installer is the only full-activity route Made can open and requires remote python3 for the shipped hook, and its hooks apply only to newly started Grok sessions, which Made must disclose.

- **Q:** How is a same-version companion whose bytes differ from the packaged set handled?
  **A:** After a confirmed mismatch, the user explicitly corrected the earlier content-addressed/build-retention direction: do not retain multiple content or build companion directories, and update the existing app-owned companion so builds do not accumulate. Initial staging and exact reuse stay unchanged; a missing, corrupt or different set under the same version produces a sanitized update-required state instead of generic `ssh connection failed` or app-version bump advice. Changed bytes require a separate `Update companion` approval for the current attempt; refusal or cancellation performs no remote write or delete. The approved fixed script stages all 11 artifacts in a private temporary sibling, verifies sizes/hashes/permissions, swaps the existing target atomically or rollback-safely, and removes temporary/replaced owned directories; any pre-swap failure leaves the original untouched and preserves actionable detail. Running companions/terminals are not killed, later companion and Grok-install launches resolve the same updated path, and a pre-attach stage/open failure shows a bounded Explorer unavailable state instead of perpetual `Loading folder…`.

No material clarification remains. Implementation must stop and evolve this contract if the selected mechanisms cannot meet these outcomes; it must not silently substitute terminal-only behavior, an auto-restarted OpenCode process, tmux, an empty poll as the end of a resnapshot, a `GROK_HOME` redirection, or a silent Grok plugin install.
