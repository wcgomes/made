# Proposal: Claude Code integration

## Intent
Made integrates OpenCode and Grok Build as terminal TUIs whose sessions drive the explorer and the workspace-tab status, but Claude Code, the third TUI users run in Made terminals, is explicitly excluded and shows as a plain shell tab. Claude Code now offers two channels that fit Made's terminal-first, local-only, no-config-edit model: the Program Status Protocol (OSC 7501) that it emits to the hosting terminal, and session-only plugins loaded from an environment variable. This change makes Claude Code the third integrated TUI using those two channels, without editing the user's Claude Code configuration and without degrading anything when either channel is missing.

## Scope
Active change `claude-code-integration`, user-requested. It adds a new domain and modifies four realized domains:
- New `specs/claude-code-session-follow.md`: catalog row and direct launch, terminal-side OSC 7501 probe reply and session-level status consumption, session-only shipped plugin via `CLAUDE_CODE_PLUGIN_DIRS` composed into local shell tabs and directly launched Claude Code tabs, metadata-only per-tab hook spool, process ownership and liveness, explorer follow with precedence OpenCode > Claude Code > Grok > shell, tab branding, dots and title, the About diagnostics row, fail-open channel behavior, the privacy and observation boundary, and a regression guarantee for OpenCode and Grok.
- `specs/grok-session-follow.md`: MODIFIED `Catalog-driven new-tab menu` (Claude Code joins the catalog after Grok; the "Claude Code and Codex MUST stay out" clause is withdrawn for Claude Code only), `Grok tab dots` and `Grok yields to OpenCode and returns to the shell` (Grok yields to a present or live Claude Code, below OpenCode).
- `specs/opencode-session-follow.md`: MODIFIED `Shell Directory Follow` (only the title clause, now explicitly scoped to cwd discovery with a cross-reference to the bounded Claude Code tooltip title) and `V1 Scope Boundary` (Claude Code becomes a supported integration; every other agent TUI stays excluded).
- `specs/made-ui-ux.md`: MODIFIED `Brand and Workspace Tabs` (a Claude Code tab's label, tooltip and leading icon are owned by the new domain, the same delegation Grok already has; nothing else changes).
- `specs/ssh-remote-workspaces.md`: MODIFIED `SSH server entry and launch choices (SSH-01)` (remote `claude` detection and a `Claude Code SSH` row) and ADDED `Remote Claude Code launch and status (SSH-11)` (direct remote launch and OSC 7501 status through the remote terminal; no remote plugin, hook, staging or write).

## Non-goals
- Remote Claude Code hooks, remote plugin staging, remote companion work, remote session follow or remote explorer follow for Claude Code; deferred to a follow-up change.
- Editing any user Claude Code file (settings, `~/.claude.json`, plugin registry, marketplaces, hooks, statusline), running `claude plugin install` or any other `claude` subcommand, or passing Claude Code command-line arguments.
- HTTP hooks to the bridge, a statusline command, the IDE lockfile/MCP channel, reading transcripts or session files, scraping screen content, and reading the window title outside the bounded tooltip case.
- Using `claude agents --json` (or any other spawned `claude` command) as an inventory fallback, even though the spike showed it works (see Clarifications).
- OSC 7501 sub-task rows (emissions with `id`); they MAY be counted in a later change. The `kind`, `title`, `msg` and `progress` fields are not used.
- Parsing the glyph prefixes Claude Code adds to its window title when it gets no probe reply; that is not a channel.
- A new unread dot treatment; a finished turn shows idle, as Grok's does. A Claude Code session map, session switching or focusing from Made.
- Answering OSC 7501 differently per program, or changing what OpenCode or Grok do beyond receiving the protocol's standard probe reply.
- A workaround that drops, reorders or replaces the user's `CLAUDE_CODE_PLUGIN_DIRS` entries. (Phase 0 found no plugin-count failure; see the decision index.)
- Codex, ACP or any other agent TUI.

## Approach
Two independent channels, each fail-open, joined only inside Made. Channel 1 (status): Made's terminal answers the OSC 7501 capability probe for any program and consumes only session-level (no `id`) `app=claude-code` emissions, mapping their `state` to the existing busy, attention and idle dot categories; a bare `state=clear` ends a live Claude Code status. Channel 2 (identity and directory): a session-only plugin shipped with Made, loaded by Claude Code from `CLAUDE_CODE_PLUGIN_DIRS`, which Made composes (never overwrites) into the environment of local shell tabs and directly launched Claude Code tabs; its native async hook appends one metadata-only record per event to a private per-tab spool, and Made claims a record only when live process ancestry ties the Claude Code process to that tab. Protocol status wins over hook-derived status when both exist; hooks alone supply session id, directory (from the latest owned record of any event) and a renamed session title. The tab tooltip title is the terminal's own window title, read only while a Claude Code protocol status is live in that tab, else the hook session title, else `Claude Code`. Explorer root precedence becomes OpenCode > Claude Code > Grok > shell. Remote SSH tabs get launch plus OSC 7501 status only. `design.md` is created because the channel trade-off, the interacting probe/emission/hook/ownership flow and the security reasoning do not fit as short decision entries.

## Decision index
- **Two channels, fail-open:** OSC 7501 for status, session-only plugin hooks for identity and directory; each works alone, neither is required, and a plain terminal remains when both are missing. Rationale and the rejected alternatives in [design.md](design.md#significant-decisions).
- **OSC 7501 receiver is app-agnostic:** Made replies to every probe with the protocol's standard reply (`ESC ] 7501 ; ? BEL`, verified to enable reporting on claude 2.1.319) and acts only on session-level `app=claude-code` emissions plus a bare `state=clear` while such a status is live. Other programs only ever see the standard reply. See [design.md](design.md#osc-7501-wire-format).
- **Session-level only:** emissions with `id` are sub-task rows and are ignored in this change, including their clears.
- **`msg` never retained:** it can carry tool commands ("approve Bash: ..."); it is never decoded into retained state, stored, logged, displayed or copied.
- **Session-only plugin via `CLAUDE_CODE_PLUGIN_DIRS`:** additive composition into local shell tabs and direct Claude Code tabs only, deduplicated, never into OpenCode, Grok or SSH launches; nothing is persisted in the user's Claude Code configuration, so there is nothing to uninstall. Plugin manifest name `made` (Claude Code's validator rejects `claude-*` names and warns on the word `claude`). `:` separator verified on POSIX; the Windows separator is a phase 0 task. The hook must keep its executable bit. See [design.md](design.md#plugin-loading).
- **Native async hook, metadata-only per-tab spool:** a Rust hook executable per local target, no interpreter; records carry time, session id, cwd, event, notification type, status, an optional sanitized session title and process ancestry, never prompt (`UserPromptSubmit.prompt`), tool input (`PermissionRequest.tool_input`), transcript path or other payload content; private 0700/0600 spool bounded to 1 MiB with 4 KiB records. See [design.md](design.md#hook-spool).
- **Ownership by live ancestry (≤32 hops):** the hook's parent is `/bin/sh -c`, Claude Code is two hops up; the Claude Code process, not the hook shell, is the liveness anchor. See [design.md](design.md#ownership-and-liveness).
- **Field mapping:** session id from the hook payload (changes on clear, resume, fork, compact and replaces the previous session of the same process); session directory = cwd of the latest owned record of that session, any event (with `claude -w`, session start reports the original directory and later events the worktree); `working` busy; `blocked` and `error` attention, with permission request and permission/idle notifications as the hook fallback; `done` and `idle` idle; no view directory; one current session per Claude Code process.
- **Tooltip title:** the terminal's OSC 0/2 title, read only while a `claude-code` protocol status is live in that tab, sanitized and capped at 120 characters; else the hook `session_title` (sent on the next prompt after an explicit rename); else `Claude Code`. OSC 7501 itself has no session title.
- **Precedence:** explorer root OpenCode > Claude Code > Grok > shell; tab presentation OpenCode active > Claude Code present > Grok open > folder. Locally Claude Code outranks Grok because a running Claude Code is in the foreground of its tab; remotely the order of SSH-10 is kept (known follow-up).
- **Two-plugin-directory risk (resolved in phase 0, not a Claude Code limitation):** the spike's "two entries never enable 7501" was an artifact of the spike responder, which answered DA1 before the 7501 probe. Phase 0 (86 runs: 54 with that responder, then 19 with an in-order responder and 13 with a DA1-first control) shows enablement is independent of plugin count, hook count, sync versus async, entry order, a nonexistent second entry, a duplicated entry and even no plugin at all; it depends on the probe reply being written before the reply to the DA1 query that follows it in the same output. With an in-order responder 19/19 runs enabled 7501 (two entries 6/6, none 4/4, one 3/3, two entries without answering DA1 3/3, two entries with a 1 s reply latency 3/3). With DA1 answered first 9/13 enabled. Classification: Made-side requirement (reply ordering), not Claude Code behavior and not unreproducible. Consequence: spec `Program status protocol in the terminal` gains an ordering MUST (the probe reply precedes any reply to a query that follows the probe in the output stream) and scenario, and tasks 1.1/1.3 gain an ordering test and mechanism. The fail-open diagnostics (`Claude Code status protocol is unavailable.`) stay for any probe without emissions; user entries are still never dropped.
- **Status protocol observed:** at least one session-level `app=claude-code` emission since that Claude Code started; the probe alone does not count, because a probe can be followed by no emissions if the reply is late, misordered, or Claude Code does not enable reporting. Used by the local and SSH-11 diagnostics.
- **Presence is its own requirement:** `Claude Code presence` defines when Claude Code is present in a tab, so the Grok and UI deltas can reference one definition.
- **Windows hook support is SHOULD:** macOS and Linux MUST run the hook; if task 0.4 shows Claude Code on Windows cannot run it, Windows fails open with hooks reported unavailable. Task 0.4 result: macOS and Windows behavior is `UNVERIFIED` (this machine is WSL Linux only); see [design.md](design.md#phase-0-results).
- **Spool cleanup by owner instance:** leftover spools are removed only when their owner Made instance is gone, so concurrent Made instances never delete or apply each other's spools.
- **Remote detection stays in the client probe:** `claude` is one more `command -v` line in the SSH-01 probe; companion `Capabilities` is not changed. `made-remote` gains only an additive `LaunchTarget::Claude` so the companion can start the remote absolute `claude` with no arguments and no shell first; it adds no plugin, environment, staging or remote write.
- **Diagnostics row ownership:** the new domain owns the Claude Code row; `Diagnostics Presentation` is not modified because it already allows rows beside the OpenCode pill.
- **Diagnostics grace period:** about 10 seconds after Claude Code becomes present before reporting a missing channel; the probe arrives 0.27 to 0.7 s after start and the first emission 20 to 50 ms after the reply, so 10 s leaves margin. Tunable at implementation without changing the states.
- **Bounds:** protocol sequences over 4096 bytes are ignored; displayed titles are at most 120 characters after sanitization.
- **Mark:** the official Claude Code mark vendored as an SVG asset, treated like `grok.svg`; the asset task records its source URL.
- **Remote scope:** launch and OSC 7501 status through the remote PTY only; remote hooks and companion staging are a follow-up change.
- **ADR 0008 (written during implementation):** "Claude Code via OSC 7501 and a session-only plugin", recording the two-channel decision, the rejected alternatives (including `claude agents --json` and title glyphs), and the security-policy update that replaces "Made does not scrape titles" with "Made consumes structured status-protocol metadata, and reads the window title only as a bounded tooltip while that structured status is live; never prompts, screen contents or titles for directories".

## Clarifications
- **Q:** What is the exact OSC 7501 field set beyond `state` and `app`, and how is the status cleared?
  **A:** Observed on claude 2.1.319 through the real `made_terminal::TerminalCore`: emissions are `ESC ] 7501 ;` plus `:`-joined `key=value` plus BEL, with fields `state`, `app`, `id`, `kind` (`permission`, `auth`), `title` and `msg`; states `idle`, `working`, `done`, `blocked`, `clear`, with `error` expected; `progress` was not observed. Entries with `id` (and a base64 `title`) are sub-task rows, and `state=clear:id=X` removes one. On exit Claude sends `working`, then three bare `state=clear` without `app`, then an empty OSC 0 title. Decision: Made uses session-level entries only, ignores `id` rows, `kind`, `title` and `progress`, never retains `msg`, and accepts a bare `state=clear` as ending the Claude Code status only while one is live in that tab.
- **Q:** Do hook payloads carry a session title, and where does the tab title come from?
  **A:** OSC 7501 has no session title. Claude sets its session title with OSC 0 (`Claude Code`, then an AI title, `/rename foo` gives `foo`, empty on exit). The hook `session_title` appears only on the next `UserPromptSubmit` after an explicit `/rename`. Decision: the tooltip title is the window title read only while a `claude-code` protocol status is live in the tab, sanitized and capped; else the hook session title; else `Claude Code`. The privacy requirement allows the window title only in that bounded case, and titles are still never used for cwd.
- **Q:** Is `claude agents --json` a usable fallback inventory?
  **A:** It lists interactive PTY sessions (Claude pid, session id, name including after rename, status idle/busy/waiting) in 0.16 to 0.4 s with a 1.4 s outlier. Decision: keep it out of the contract and out of this change; it spawns `claude`, which the metadata-only detection rule avoids.
- **Q:** Which Claude Code mark does Made paint?
  **A:** The official Claude Code mark, vendored as an SVG asset with the same treatment as `grok.svg` in the 16px leading slot. The spec states only "official Claude Code mark"; the exact source and colors are an implementation task that records the source URL.
- **Q:** Which hook record provides the session directory?
  **A:** The cwd of the latest owned record of that session, whatever its event, because `CwdChanged` and `StopFailure` did not fire in tests and with `claude -w` only events after session start carry the worktree directory.
- **Q:** Should Made parse the title glyphs Claude Code shows without a probe reply (`✳` idle, `◐`/`◑` working)?
  **A:** No; they are not a channel. Without the protocol, status comes from hooks.
- **Q:** What happens when `CLAUDE_CODE_PLUGIN_DIRS` has two entries and 7501 never enables?
  **A:** Phase 0 isolated it: not a two-entry effect. The earlier spike responder wrote the DA1 reply before the 7501 probe reply, and Claude Code then did not enable reporting in about 70% of runs (37 of 54) regardless of plugin configuration; with the probe reply written first (stream order) it enabled in every run. See the decision index entry. The spec stays fail-open: hooks still drive dots and explorer, diagnostics reports `Claude Code status protocol is unavailable.` for any probe without emissions, and Made never drops the user's entries.
- **Q:** Is the remote precedence divergence (remote Claude Code yields to SSH-10 Grok) acceptable?
  **A:** Yes, for now; recorded as a known follow-up to harmonize after `grok-native-hook` archives. SSH-11 states explicitly that, unlike SSH-10 for Grok, it does not mirror the local contract.
- **Q:** Should the realized `Shell Directory Follow` title clause be left alone or modified? (coordinator decision during `analyze`)
  **A:** Modified. The MODIFIED copy is verbatim except the title clause, which now reads as cwd-discovery scope, says a window title is never a cwd source, and cross-references the bounded tooltip-title allowance owned by `Claude Code privacy and observation boundary`.
- **Q:** Does a capability probe count as the status protocol being observed? (`analyze` finding)
  **A:** No. Only a session-level `app=claude-code` emission counts, because a probe can be followed by no emissions if the reply is late, misordered, or Claude Code does not enable reporting.
