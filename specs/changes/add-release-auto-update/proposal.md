# Proposal: Installable releases with in-app auto-update

## Intent
Made currently ships only unsigned debug development artifacts that are not installers, cannot update themselves and whose packaged layout has never been launched end-to-end. End users need a single obvious place to download Made, a simple install on each supported OS with nothing else to install first, and an app that keeps itself current without breaking the install.

## Scope
This is the active change `add-release-auto-update` for the new domain `release-distribution`; its source spec `specs/release-distribution.md` does not exist yet and will be created on first archive. The delta ADDS REL-01 to REL-12: a GitHub Release produced from a `v*` tag with release-profile builds for aarch64-apple-darwin, x86_64-apple-darwin, x86_64-unknown-linux-gnu and x86_64-pc-windows-msvc; a single version source shared by the app and both bundled plugins; a complete, launchable installed layout (made-app, plugins/opencode-made, plugins/grok-made, remote/<target>/made-remote companions, made-askpass, LICENSE); self-contained installation on a defined OS baseline; per-OS install and unsigned first-run guidance; update discovery, background download, user-confirmed apply and restart, integrity, failure safety, an opt-out, update-path continuity, and no self-update for non-installed builds. It MODIFIES `Minimal Workspace Layout`, `About Presentation` and `Keyboard Focus and Accessibility` in `specs/made-ui-ux.md` to add the wordmark update indicator, its `About, update ready` name and the About Updates section. REL-03 and REL-04 depend on the active change `specs/changes/grok-native-hook/`, written in parallel and not edited here, which replaces the Python Grok hook with a native per-target executable inside `plugins/grok-made`. The realized `Cross-Platform Delivery` requirement is unchanged because development artifacts continue. Archive order: this change MUST archive before or together with `grok-native-hook`, because that change cites REL-02 for its version policy.

## Non-goals
- Code signing, notarization, or publisher-identity verification on any OS.
- Homebrew, winget, Linux distribution repositories, app stores, or any channel other than GitHub Releases.
- Linux formats other than AppImage; a universal macOS binary.
- Prerelease or beta channels, and publishing prerelease tags.
- Staged or percentage rollouts, server-side rollout control, kill switches, or update telemetry; a defective release is remediated by publishing a newer release.
- Downgrade or user-selectable rollback to an older version.
- Windows arm64, Linux arm64, or any target beyond the four listed.
- Enterprise or managed deployment (MSI, group policy, silent fleet install).
- Restart persistence of open workspaces across an update restart.
- Changes to OpenCode, Grok, SSH, explorer, terminal, or preview behavior.
- Wiki edits other than the scoped release-procedure task (8.2 in tasks.md, `wiki/operations/release-ci.md`); other descriptive knowledge is updated by a post-implementation ingest.

## Approach
Record the outcome as a new-domain delta plus three MODIFIED UI requirements. Releases are built by a tag-triggered workflow that reuses the `ci-artifacts.yml` staging layout and companion assembly with release-profile binaries, packages each target with Velopack on its own runner, smoke-tests the installed layout, publishes installers, update packages, update feeds and `SHA256SUMS` to one GitHub Release only after every target passes, and then runs a post-publish upgrade check from the previous release. The app integrates Velopack's Rust update client behind `made-platform`, with scheduling, preference and UI state in `made-app`. Unverified Velopack behavior is settled by early probe tasks, each with a stated fallback, before dependent implementation. `design.md` is not created: the update flow and probe fallbacks fit the spec, short decisions and tasks without overload.

Conflicts and facts flagged against descriptive knowledge and the live contract, not silently resolved:

This is the realized rule applied, not new behavior.
- `wiki/operations/release-ci.md` states there is no installer, signing, package repository or auto-update path and that the packaged layout has never been launched end-to-end; this change supersedes the first part and makes installed-layout launch release-blocking (REL-03). The page also already omits `ci-ssh-remote.yml`, grok-made, companions and askpass.
- `wiki/security.md` says "no telemetry or off-device state transfer in v1". Update checks make outbound HTTPS requests to GitHub that reveal client address, platform and installed version. This is not telemetry; REL-06 bounds what may be sent.

- `AppPaths` resolves the OpenCode plugin at `<install_root>/plugins/opencode-made`, where macOS `install_root` is the bundle's `Contents/Resources`, while `crates/made-app/src/ssh_servers.rs` resolves `remote/<target>/made-remote` and `made-askpass` next to the executable (`Contents/MacOS`). The installed macOS layout must satisfy both (probe task 1.3).
- `grok-native-hook` owns the Grok hook build, the `.github/scripts/stage-grok-plugin.sh` staging script, the 10-artifact companion set in `.github/scripts/assemble-desktop-package.py`, and the release-build resolution of the install-root grok-made copy in `made-platform`. This change consumes them: shared staging calls `stage-grok-plugin.sh`, and REL-03's manifest check uses the 10-artifact manifest. Overlapping files and ordering are listed in tasks.md under Cross-change dependencies.
- `README.md` states there are no installers or auto-update channels; task 8.1 replaces that text.
- Linux release binaries move to an `ubuntu-22.04` runner for the glibc 2.35 floor; development artifacts keep their current runner.

## Decision index
- **Distribution channel:** GitHub Releases only; Homebrew and winget may later be added as thin channels over the same assets.
- **Installer and updater:** Velopack provides per-OS installers and the in-app update client, fed from GitHub Releases. Chosen for one cross-platform toolchain with a Rust client and GitHub Releases support.
- **No signing or notarization:** builds stay unsigned; Gatekeeper and SmartScreen friction, including a possible repeat after an update, is accepted and documented (REL-05). Residual: update integrity rests on HTTPS to GitHub and the hash in the release's own feed, so anyone able to publish a release on the repository can ship an update; REL-08 states this limit.
- **Trigger and versions:** a pushed `v*` stable tag, newer than the latest published stable release, produces the release, which is marked latest explicitly. `[workspace.package].version` is the single version source; CI fails on drift and the release refuses any disagreement (REL-02). Prerelease tags are refused.
- **Version bump mechanism (fallback chosen):** stamping plugin versions only at staging was rejected because the repository plugin copies are consumed directly. `AppPaths` development builds load the repository `plugins/opencode-made` when no staged copy exists, so OpenCode reads its `package.json` and the plugin reports the `PLUGIN_VERSION` constant in `plugins/opencode-made/src/protocol.ts` in its hello, which Diagnostics shows. `plugins/opencode-made/tests/lifecycle.test.ts` asserts that constant. `ci-artifacts.yml` reads the repository `package.json` version into `version.json`. The repository `plugins/grok-made/plugin.json` is the source that `stage-grok-plugin.sh` copies. Therefore `scripts/bump-version.sh X.Y.Z` rewrites all version sites (workspace `Cargo.toml`, both plugin manifests and `PLUGIN_VERSION`), refreshes `Cargo.lock` through cargo and `plugins/opencode-made/package-lock.json` through `npm version X.Y.Z --no-git-tag-version`, and also updates the `appVersion` example in `plugins/opencode-made/README.md`; `check-versions.py` in CI fails on drift; the plugin test compares against `package.json` instead of a literal. `grok-native-hook` 2.6 additionally stamps the workspace version into the staged grok-made `plugin.json`, which is consistent with this rule.
- **Upgrade verification (user decision; no test repository):** no test repository and no build-time update-location override exist; REL-08 has no exceptions. REL-12 is verified by a post-publish upgrade check workflow (manually triggered and called after each release) that, per target, installs the previous published release from the production repository and updates it through the real in-app path, optionally via a non-interactive command-line entry using the same client, allowlist and verification, to the latest release. A failed check is remedied by a fixed newer release. Smoke keeps a marker asserting the production owner/repo.
- **Privacy check at the client boundary:** a recording HTTPS proxy against the production repository would require trusting an intercepting CA, which changes the client's trust rules, so REL-06's request-content guarantee is tested at the client boundary by asserting the URL and headers the update source builds for a check (task 4.2).
- **Rollout plan (operational, not a requirement):** during implementation, real tags and releases are cut in the production repository as needed (`v0.1.0`, then `v0.1.1`, `v0.1.2`, ...) so the upgrade check runs between real releases. Their release notes are labelled clearly as temporary test releases. Once implementation is verified, the coordinator deletes all those releases, then their tags, and re-releases `v0.1.0` from the final commit; "first" and "second published release" count from that final `v0.1.0`. The monotonic-tag gate stays compatible because no published release remains at that point. Cleanup on every machine that installed an iteration release:
  - uninstall Made, because `0.1.0` is lower than the installed version;
  - run `grok plugin uninstall grok-made --confirm` locally and on each SSH server where Made installed it, because an iteration grok-made version higher than `0.1.0` would otherwise be left in place;
  - remove Made's staged remote version directories on each SSH server.
- **Publish hardening:** a `v*` tag ruleset restricts creating, updating and deleting matching tags to a maintainer bypass list. GitHub rulesets cannot key on release state, so the rule against re-tagging a published version is procedural (8.2). Publishing runs in a protected `release` environment with required approval; release jobs restore no caches and pin third-party actions by commit SHA; `contents: write` is granted only in the publish job. GitHub immutable releases MAY be enabled only after the final `v0.1.0` re-release, never before, because the rollout deletes the iteration releases. The ruleset, the environment and immutable releases are manual maintainer steps documented in 8.2, not automated and not configured by implementers.
- **REL-01 approval gate (user decision):** the gate is the maintainer as required reviewer on the protected `release` environment, plus a deployment policy that allows only `v*` tags. The coordinator configures both manually at the end of implementation. Rollout exception: iteration releases `v0.1.0` to `v0.1.7` were published before this gate existed. The gate is configured before the final `v0.1.0` re-release, and that re-release happens only after the Phase 11 checkpoint in tasks.md passes.
- **Test seams:** the injectable source/transport used by the 4.2 tamper, redirect and allowlist tests exists only behind a test-only, non-default cargo feature; release builds never enable it (checked by 7.6 and 7.7). The local feeds used by the probe crate (1.1–1.7) are not product code and are not a REL-08 exception.
- **Targets and formats:** Windows x64 installer; macOS arm64 and x64 separately, each with Velopack's default `.pkg` installer and portable `.zip`; Linux x64 AppImage only.
- **Per-user installs:** install and update need no administrator rights on any OS.
- **OS baseline:** Windows 10 1809+ and Windows 11; macOS 12+ (binaries declare minimum OS 12.0); Linux glibc 2.35+ (built on `ubuntu-22.04`) with glibc, `libgcc_s.so.1`, libxkbcommon, Wayland/X11 client libraries, EGL/GL and a Vulkan loader assumed present; acceptance on Ubuntu 22.04, Ubuntu 24.04 and current Fedora.
- **Self-contained mechanisms:** statically link the MSVC C runtime (`crt-static`) for Windows binaries, with app-local VC++ runtime DLLs as fallback (task 1.6); build the release askpass in the release job with the same floors; enforce the glibc floor and the ELF `NEEDED` allowlist in the release build, with runtime-loaded libraries covered by fresh-distribution acceptance; the AppImage runs without libfuse or `fusermount` (task 1.4); Velopack's own binaries meet the same rule (task 1.5).
- **Update policy:** automatic checks on by default, at launch and every 24 hours while running, plus manual `Check for updates` in About; single stable channel, GitHub prereleases never offered; background download after discovery; apply and restart only after confirmation in About; a declined update is kept and re-offered at next launch, never applied silently at quit or launch.
- **Update surface:** a discreet accent dot on the MADE wordmark when an update is ready; status, manual check, opt-out toggle, restart action and inline confirmation live in About (MODIFIED UI requirements).
- **Checksums:** every release publishes `SHA256SUMS` for all assets, documented as corruption detection only.
- **Update integrity:** HTTPS only; an exact GitHub host allowlist enforced on every redirect hop, with GitHub URLs pinned to the project repository path; SHA-256 and embedded-version checks before ready. The final host list is recorded from probe 1.8 observations.
- **Development artifacts stay:** `ci-artifacts.yml` continues alongside releases; the staging logic is shared rather than duplicated.
- **Native Grok hook:** delivered by `specs/changes/grok-native-hook/`; a prerequisite for publishing a release under REL-04.
- **License:** MIT; `license = "MIT"` is added to `[workspace.package]` and LICENSE ships in every package.
- **Optional integrations are not prerequisites:** OpenCode, Grok Build, host OpenSSH and host git stay optional and degrade as the realized specs define.
- **No design.md:** reapply the overflow rule if a probe fallback changes the update flow materially.
- **Probe outcomes (1.8, release-probe.yml runs 42062557947, 42064109555, 42068108063):**
  - **Velopack:** crate `velopack = "=1.2.161"` with `public-utils` (needed to implement `UpdateSource`, which names `bundle::Manifest`, and to read package manifests) and `vpk` 1.2.161, the latest non-prerelease. API used: `VelopackApp::build().set_auto_apply_on_startup(false).set_locator(..).run()`, `locator::auto_locate_app_manifest(LocationContext::FromCurrentExe)` / `VelopackLocator`, `bundle::load_bundle_from_file(..).read_manifest()`, `UpdateSource`, `VelopackAsset(Feed)`, `process::wait_for_pid_to_exit`; apply runs the shipped updater (`Update.exe` / `UpdateMac` / `UpdateNix`) as `apply --package <nupkg> --root <root> --packageDir <dir>` (`--waitPid` for the About restart; `--silent --norestart` for the command-line apply).
  - **1.2 (pass with fallbacks):** auto-apply on startup can be disabled (no return to the user); installed vs non-installed detection works through the locator (non-installed builds fail location and make no request); each pack carries its explicit channel. The built-in sources follow redirects to any host (a loopback `302` to another host was followed) and send `localVersion`, `id` and an install identifier `stagingId`, so fallback "custom update source in `made-platform`" applies. Velopack verifies SHA-256 only when the feed lists one (otherwise SHA-1) and never the embedded version, so fallback "`made-platform` performs both" applies; Made also downloads itself, so a failed newer download never deletes an older ready package.
  - **Request observability:** the request is observable at the transport layer (loopback capture). Made's request is `GET /wcgomes/made/releases/latest/download/releases.<channel>.json` with exactly `host`, `user-agent: Made/<version> (<os>; <arch>)`, `accept` and `accept-encoding: gzip`; no query string, cookie or identifier.
  - **REL-08 hosts (observed):** `github.com` (`/releases/latest/download/` and `/releases/download/<tag>/` redirect within the repository path) → `release-assets.githubusercontent.com`; `objects.githubusercontent.com` kept as GitHub's older asset host. `api.github.com` is not used and is not allowed.
  - **1.3 (pass with fallbacks):** `vpk` accepts a prebuilt `.app` as `--packDir`, so the bundle is composed with `Contents/Resources/{plugins,LICENSE,README.md,version.json,remote}` and `Contents/MacOS/{made-app,made-askpass}`, with `Contents/MacOS/remote` a relative symlink to `../Resources/remote`: non-Mach-O files under `Contents/MacOS` lose their signature in the nupkg (xattrs are not preserved) and failed `codesign --verify` after an update. The `.pkg` installs for the current user without admin (`installer -target CurrentUserHomeDirectory` → `~/Applications/Made.app`). Signature fallback: unsigned output failed `codesign --verify` (x64 "not signed at all", arm64 "no resources but signature indicates they must be present"), so packaging ad-hoc signs through `vpk --signAppIdentity -` (no identity); `codesign --verify --deep --strict` then passes after install and after a v1→v2 update, which relaunched. `spctl` rejects the app (unsigned), so the documented Gatekeeper path applies: macOS 15 — open Made, choose Done, open System Settings › Privacy & Security, choose Open Anyway for Made and confirm with the login password; macOS 12–14 — Control-click Made, choose Open, then Open. The same applies to the `.pkg`. Click-through on a fresh machine is task 9.1 evidence.
  - **1.4 (fallback A accepted):** Velopack's static type-2 runtime refuses to start without `fusermount` on Ubuntu 22.04 and 24.04. The AppImage runtime is replaced in post-processing by uruntime v0.8.1 `uruntime-appimage-squashfs-x86_64` (static, sha256 `2153e68d63f570c7ebe3d1f38df0fa16814f34d839c5cce2ee42667e327708e8`) with `APPIMAGE_EXTRACT_AND_RUN=1` embedded (`--appimage-addenvs`), and the nupkg and feed digests are rewritten; without the embedded variable uruntime fails on 24.04, whose AppArmor blocks unprivileged user namespaces. With it, launch (≈0.1 s extraction) and a v1→v2 update work with libfuse and `fusermount` absent on both runners. Linux packages live in `<data_dir>/updates` (private, same filesystem as the user's files) instead of the shared `/var/tmp/velopack`.
  - **1.5 (pass):** `Setup.exe` and `Update.exe` import only in-box DLLs (advapi32, bcrypt, combase, comctl32, gdi32, kernel32, ntdll, ole32, oleaut32, propsys, psapi, shell32, user32, ws2_32) and request `asInvoker`; install is per-user under `%LocalAppData%\Made` with a Start menu shortcut and an HKCU uninstall entry. `UpdateMac` links only system frameworks and `/usr/lib` libraries with minos 10.12 (x64) / 11.0 (arm64). `UpdateNix` and the runtime are static (no `NEEDED`).
  - **1.6 (pass):** with `+crt-static`, `made-app.exe`, `made-askpass.exe` and `made-grok-status.exe` import no `VCRUNTIME*`, `MSVCP*` or `api-ms-win-crt-*` DLL and the smoke test passes; no app-local runtime is needed.
  - **1.7 (pass):** the four channels produce non-colliding feed files (`releases.<channel>.json`, `Made-<version>-<channel>-full.nupkg`); end-user downloads are not feed-referenced, so renaming them keeps updates working; a higher prerelease-style feed entry is chosen by Velopack's own selection and ignored by Made's stable-only filter; killing the updater before the swap, during extraction and after the swap left a launchable previous or new version on every OS. Swap atomicity from Velopack 1.2.161 source: macOS `renamex_np(RENAME_SWAP)` (atomic; falls back to two renames if the volume refuses); Linux `mv -f` of the AppImage (atomic `rename(2)` when the packages directory and the AppImage share a filesystem, a copy otherwise); Windows renames `current` aside, then the new directory in (two renames, not atomic). Power loss is therefore unverified on Windows and on Linux layouts that cross filesystems.
  - **AppImage extraction target (M2, decided):** the probe (`release-probe.yml`, job `appimage-extract-dir`) reproduced the issue: uruntime v0.8.1 extract-and-run reuses `$TMPDIR/appimage_extracted_<name><hash>`, whose hash is predictable (image, runtime and uid), and runs any non-empty existing directory there without checking its owner, so a second local user's planted directory ran (`PWNED-BY-ATTACKER`). Chosen fix, in `linux-appimage-runtime.py`. The control is a private per-user location: the embedded `APPIMAGE_TARGET_DIR=${HOME}/.cache/made/appimage-<version>-<hash>` (expanded by the runtime; it overrides `TMPDIR` and is removed from Made's environment) puts the target in the user's home, which other users cannot create or replace, and names it by the first 16 hex digits of the image's SHA-256 so two builds of one version never share an extraction. `$XDG_RUNTIME_DIR` with a `$HOME/.cache` fallback was preferred but cannot be expressed: uruntime v0.8.1 expands only plain `${NAME}` references in its embedded settings, with no default value, and a target under an unset `$XDG_RUNTIME_DIR` would leave Made unable to start. The rebuilt squashfs root is mode 0700, so a fresh extraction is private. The image's `AppRun` is a guard, kept as defence in depth: it runs Velopack's `AppRun` only when the extraction directory is a real directory (not a symlink) owned by the user with no `077` bit and its parent is owned by the user (the guard then sets the parent to 0700), and otherwise exits 1 with a clear message. Because uruntime runs any non-empty target as is, the guard also checks every file against a SHA-256 manifest built into the image; an interrupted or damaged extraction is removed and the AppImage is started once more to extract afresh, and if that copy is also incomplete Made exits with a clear message, so an interrupted extraction never leaves Made unable to start. It also clears `APPIMAGE_EXTRACT_AND_RUN` before Made starts. Evidence: `test_linux_appimage_runtime.py` (guard unit cases) and the AppImage-level `smoke-installed.py` run on Ubuntu 22.04 and 24.04 against a target owned by another user, a group/other-writable target, a symlink, a target with a file cut short and a target with most files missing. Constraint (user decision, now REL-04): the target is private per user; a reused extraction directory that is not owned by the user, or whose mode has any `077` bit set, is never used.
  - **Windows command-line apply (security review):** Velopack replaces `current\` and stops processes inside it, so the invoked command-line process must exit before the swap, and the apply is handed off to a temp-copy helper. REL-12 now defines this hand-off: the lock is held without a gap through the helper's swap, GUI startup is refused for the whole period, the entry reports a hand-off (not completion) and exits 0 only if the hand-off succeeded, and the helper outcome is reported by the next invocation and in About diagnostics. Tasks 11.1–11.6.

## Clarifications
- **Q:** Which Linux formats ship?
  **A:** AppImage only.
- **Q:** macOS separate per-architecture packages or universal?
  **A:** Separate arm64 and x64 packages.
- **Q:** macOS install form and admin rights?
  **A:** Velopack default outputs, a `.pkg` installer and a portable `.zip`; per-user, with no administrator rights for install or update.
- **Q:** Minimum supported OS versions?
  **A:** Windows 10 1809+ and Windows 11; macOS 12+; Linux built on `ubuntu-22.04`, giving a glibc 2.35 floor.
- **Q:** Linux library baseline and acceptance distributions?
  **A:** glibc, `libgcc_s.so.1`, libxkbcommon, Wayland/X11 client libraries, EGL/GL and a Vulkan loader are assumed present; acceptance on Ubuntu 22.04, Ubuntu 24.04 and current Fedora.
- **Q:** May the AppImage need host FUSE?
  **A:** No; it must run without libfuse or `fusermount` installed. The plan verifies Velopack's AppImage runtime early, with an explicit fallback decision.
- **Q:** Is a repeated Gatekeeper/SmartScreen approval after an update acceptable?
  **A:** Yes, as documented friction; it is not release-blocking.
- **Q:** Are update checks on by default?
  **A:** Yes; the user can disable them.
- **Q:** Check frequency?
  **A:** At launch and every 24 hours while running, plus a manual `Check for updates` in About.
- **Q:** Channels and prereleases?
  **A:** One stable channel; GitHub prereleases are never offered. Derived decision: the release pipeline refuses prerelease tags, so no prerelease publishing path is built.
- **Q:** Where does update UI live?
  **A:** A discreet indicator on the About entry point (the wordmark); notice, restart action, manual check and opt-out inside About, via MODIFIED `About Presentation` and `Minimal Workspace Layout`. Derived decisions: the indicator shows only while a verified update is ready, and the restart confirmation is inline in the About card.
- **Q:** Automatic or confirmed download?
  **A:** Automatic background download after discovery; apply and restart only after confirmation.
- **Q:** What happens on a declined restart?
  **A:** The downloaded update is kept and re-offered at next launch, not applied silently at quit.
- **Q:** Publish installer checksums?
  **A:** Yes, `SHA256SUMS` for all assets in every release.
- **Q:** Keep `ci-artifacts.yml`?
  **A:** Yes, alongside releases; `Cross-Platform Delivery` is unchanged.
- **Q:** What is the first release version?
  **A:** `0.1.0` everywhere, final. Iteration releases from the rollout plan may leave higher versions installed, which the rollout cleanup removes. grok-made goes from 0.1.1 to 0.1.0 under `grok-native-hook`, which records the developer-machine uninstall step.
- **Q:** What is the version source?
  **A:** `[workspace.package].version` only; `plugins/grok-made/plugin.json` and `plugins/opencode-made/package.json` must equal it; CI fails on mismatch and the release refuses a tag on any disagreement.
- **Q:** How many places does a version bump touch?
  **A:** Exactly one maintainer action. Stamping at staging is preferred where nothing reads the repository copy directly; otherwise `scripts/bump-version.sh X.Y.Z` rewrites all version sites with a CI drift check. Outcome: repository-direct consumers exist, so the bump script is used (see Decision index).
- **Q:** Is `libgcc_s.so.1` allowed on Linux, or must libgcc be linked statically?
  **A:** `libgcc_s.so.1` is part of the REL-04 Linux baseline; no `-static-libgcc`.
- **Q:** Does a manual check work with automatic checks off?
  **A:** Derived decision: with automatic checks off, an explicit `Check for updates` still performs one check and its download, because the user asked for it.
