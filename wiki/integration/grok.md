# Grok

Grok is one entry of the integrated-TUI catalog (OpenCode, Grok, then [Claude Code](claude-code.md)) behind the Open workspace launch bar; undetected programs get no button. Detection is the shared metadata-only `PATH` lookup (macOS Finder/Dock launches: [launch PATH](../runtime/terminal-first.md#macos-gui-launch-path)) and does not delay shell or explorer startup. Launch bar layout: [Layout and controls](../ui/layout-and-controls.md#open-workspace-screen).

The catalog label is `Grok Build`; its 16px mark is `crates/made-app/assets/grok.svg` (the two paths from https://grok.com/images/favicon.svg, fill #FCFCFC, viewBox "56 56 400 400"). While OpenCode is not active, a running Grok TUI (even before a session exists) or a shell tab with open Grok sessions paints that mark in the tab's leading slot and is labelled with the session title, else `Grok Build`; when Grok is gone and no session remains, the tab returns to the shell label and terminal glyph. Contract: `Grok tab dots` and related requirements in [`grok-session-follow.md`](../../specs/grok-session-follow.md); label rules: `Brand and Workspace Tabs` in [`made-ui-ux.md`](../../specs/made-ui-ux.md). OpenCode keeps `opencode.svg` and its launch injection; see [OpenCode bridge](opencode.md).

The Grok Build launch button starts the absolute `grok` path with the argument `dashboard` as the PTY child of a new tab in the effective launch path, with no shell first, and the current tab keeps running. Made does not inject the plugin into the Grok launch and does not hand-edit Grok `config.toml`. Grok honors `BROWSER`, so its URLs go to the ask-before-open card ([URL open requests](../runtime/terminal-first.md#url-open-requests)).

After PATH detection reports grok, Made runs the official install of the shipped `plugins/grok-made` with trust, on background work that does not block startup. The installed copy lives under `$GROK_HOME/installed-plugins/` (default `~/.grok`). An explicit catalog without detection does not install. The shipped package carries the native hook `made-grok-status` (`made-grok-status.exe` on Windows) for the host target, built from [`crates/made-grok-hook`](../../crates/made-grok-hook); no Python or other interpreter is a prerequisite. Install failure still lets Grok start, and Made records that session-status hooks are unavailable. Uninstall remains `grok plugin uninstall grok-made --confirm`, and Made does not run it.

Made and the native hook resolve the Grok home with one rule: a non-empty `GROK_HOME`, else `std::env::home_dir()` joined with `.grok` (`USERPROFILE` on Windows). Never look up `HOME` alone: Windows GUI launches have no `HOME`, which silently breaks install detection and session follow. The single resolver is `grok_home_dir()` in [`plugin.rs`](../../crates/made-app/src/integrations/grok/plugin.rs), shared by the install check, the status log, and the session inventory.

The session-follow contract is [`spec.md`](../../specs/grok-session-follow.md). Revealed About diagnostics show one Grok Build status row only after “Show diagnostics”, beside the OpenCode and Claude Code rows and not in the workspace chrome; outcomes are checking, not on PATH, installing, hooks unavailable, and an explicit catalog that did not detect does not install. The ready outcome appears only while that workspace's Grok process is still alive or its shell has an open Grok session; when the plugin is installed and Grok is not running there, the row stays inactive. Focusing an already-open Grok session does not move the explorer.

## SSH workspaces

With a saved server selected on the Open workspace screen, the launch bar offers `Terminal SSH`, plus `OpenCode SSH`, `Grok SSH` and `Claude Code SSH` when that server's bounded remote detection finds each program. Grok detection is `command -v grok` on the non-interactive remote `PATH`, falling back to `$HOME/.grok/bin/grok`, `$HOME/.local/bin/grok` and `$HOME/.cargo/bin/grok`, because the Grok installer adds `~/.grok/bin` only through interactive rc files that an SSH command never reads. One resolver serves all four consumers (the probe script `PROBE` in [`ssh.rs`](../../crates/made-platform/src/ssh.rs), then `detect_grok` in [`grok.rs`](../../crates/made-remote/src/grok.rs) used by capabilities and launch in `main.rs`, the `--install-grok-plugin` install mode, and supervisor capabilities); a new consumer must reuse it or the launch button and the install can disagree. Claude Code detection stays `PATH`-only. `Grok SSH` starts the detected remote `grok` with the single `dashboard` argument directly in a tab bound to that server and remote directory, with no shell first and no injected plugin configuration; typing `grok` in a remote shell remains the manual path and gets no `dashboard` argument. The remote surface reuses the local presentation: label and mark, session dots, newest-session explorer follow, tooltip, diagnostics row, the shared root and presentation order (OpenCode, then [Claude Code](claude-code.md#ssh), then Grok, as locally), and the remote shell label when Grok is no longer running and no session remains, all from the owning tab's remote state. The contract is [`specs/ssh-remote-workspaces.md`](../../specs/ssh-remote-workspaces.md); SSH-10 is the Grok part.

For session follow, the server-side companion reads only two Grok-native state files under the remote `$GROK_HOME` (`~/.grok` when unset): `active_sessions.json` about once a second, and appended lines from `made-grok-status.jsonl`. The inventory tier needs no plugin, consent, or remote write; owned sessions appear from live process ancestry, and sessions seen only there show idle. Hook activity requires an installed `grok-made` equal to or newer than the shipped package version (the workspace version, 0.1.0 at the first release); there is no `python3` requirement and no python3-missing state, and otherwise the tab stays on inventory with session-status hooks reported unavailable. A user-installed equal/newer plugin supplies hooks without Made consent because Made writes nothing, while Made's official installer needs its own per-server/version consent after companion staging. The shipped native hook records the Grok parent pid, so owned events apply immediately and unproven events do not cross tabs even though the hook log is server-global.

The remote stage set is 14 artifacts: `made-remote`, five OpenCode plugin files, the Grok `plugin.json`, `README.md`, `hooks/hooks.json` and `hooks/bin/made-grok-status`, and the Claude Code `.claude-plugin/plugin.json`, `README.md`, `hooks/hooks.json` and native `made-claude-status` hook (added in v0.1.2 by [`ssh-claude-code-parity`](../../specs/changes/archive/20261126-ssh-claude-code-parity/proposal.md)); both hooks are built under the same glibc 2.31 / macOS 12 floors as `made-remote`. See [ADR 0006](../decisions/0006-native-grok-hook.md).

Host-companion parity covers 16 Grok scenarios plus 15 intended-failure controls over a real loopback `sshd`; debug and release workspace test gates pass, and teardown leaves no companion or supervisor processes. The live plantsuite/native GUI matrix remains pending, so no external-server validation is claimed.
