# Grok

The `+` menu is one integrated-TUI catalog, not an OpenCode-only list. Catalog order is OpenCode, then Grok. Undetected programs are omitted. When no catalog TUI is detected and no SSH server is saved, `+` opens the folder picker and shows no menu. When any is detected or a server is saved, `Terminal` stays the first row and still opens the folder picker; detected catalog rows follow, then each saved server's SSH launch rows. Detection remains the existing metadata-only `PATH` lookup and does not delay shell or explorer startup. The `+` tooltip stays “Open folder”.

The Grok row label is Grok Build. Its 16px leading slot paints the official mark in `crates/made-app/assets/grok.svg` (the two paths from https://grok.com/images/favicon.svg, fill #FCFCFC, viewBox "56 56 400 400"). While OpenCode is not active, a running Grok TUI — even before a session exists — or a shell tab with open Grok sessions shows that same `Grok Build` label and official mark in the workspace tab's 16px leading slot. The tooltip is the session summary when sessions exist and omits the workspace path. When that Grok is no longer running and the tab has no open Grok sessions, the tab returns to the folder label and the terminal glyph. OpenCode, when active, keeps its label, icon, and dots. OpenCode keeps `opencode.svg` and its launch injection; see [OpenCode bridge](opencode.md).

Choosing Grok starts the absolute `grok` path with the argument `dashboard` as the child of a new home-directory tab, with no shell first and no picker, and the current tab keeps running. Made does not inject the plugin into the Grok launch and does not hand-edit Grok `config.toml`.

After PATH detection reports grok, Made runs the official install of the shipped `plugins/grok-made` with trust, on background work that does not block startup. The installed copy lives under `$GROK_HOME/installed-plugins/` (default `~/.grok`). An explicit catalog without detection does not install. Install failure still lets Grok start, and Made records that session-status hooks are unavailable. Uninstall remains `grok plugin uninstall grok-made --confirm`, and Made does not run it.

The session-follow contract is [`spec.md`](../../specs/grok-session-follow.md). Revealed About diagnostics show one Grok Build status row only after “Show diagnostics”, next to the OpenCode status pill and not in the workspace chrome; outcomes are checking, not on PATH, installing, hooks unavailable, and an explicit catalog that did not detect does not install. The ready outcome appears only while that workspace's Grok process is still alive or its shell has an open Grok session; when the plugin is installed and Grok is not running there, the row stays inactive. Focusing an already-open Grok session does not move the explorer.

## SSH workspaces

For a registered SSH server, the `+` flow offers `Terminal SSH`, plus `OpenCode SSH` and `Grok SSH` when that server's bounded remote `PATH` lookup detects each program. `Grok SSH` starts the detected remote `grok` with the single `dashboard` argument directly in a tab bound to that server and remote directory, with no shell first and no injected plugin configuration; typing `grok` in a remote shell remains the manual path and gets no `dashboard` argument. The remote surface reuses the local presentation: exact `Grok Build` label and mark, session dots, newest-session explorer follow, tooltip, diagnostics row, OpenCode precedence in the shared root order, and the server-name label when Grok is no longer running and no session remains, all from the owning tab's remote state. The archived contract is [SSH remote workspaces](../../specs/changes/archive/20261105-ssh-remote-workspaces/spec.md); SSH-10 is the Grok part.

For session follow, the server-side companion reads only two Grok-native state files under the remote `$GROK_HOME` (`~/.grok` when unset): `active_sessions.json` about once a second, and appended lines from `made-grok-status.jsonl`. The inventory tier needs no plugin, consent, or remote write; owned sessions appear from live process ancestry, and sessions seen only there show idle. Hook activity requires an installed `grok-made` equal to or newer than the shipped 0.1.1 package and remote `python3`; otherwise the tab stays on inventory with session-status hooks reported unavailable. A user-installed equal/newer plugin supplies hooks without Made consent because Made writes nothing, while Made's official installer needs its own per-server/version consent after companion staging. The shipped 0.1.1 hook records the Grok parent pid, so owned events apply immediately and unproven events do not cross tabs even though the hook log is server-global.

Host-companion parity covers 16 Grok scenarios plus 15 intended-failure controls over a real loopback `sshd`; debug and release workspace test gates pass, and teardown leaves no companion or supervisor processes. The live plantsuite/native GUI matrix remains pending, so no external-server validation is claimed.
