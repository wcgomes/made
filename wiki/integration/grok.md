# Grok

The `+` menu is one integrated-TUI catalog, not an OpenCode-only list. Catalog order is OpenCode, Grok, then Claude Code (see [Claude Code](claude-code.md)). Undetected programs are omitted. When no catalog TUI is detected and no SSH server is saved, `+` opens the folder picker and shows no menu. When any is detected or a server is saved, `Terminal` stays the first row and still opens the folder picker; detected catalog rows follow, then each saved server's SSH launch rows. Detection remains the existing metadata-only `PATH` lookup (macOS Finder/Dock launches: [launch PATH](../runtime/terminal-first.md#macos-gui-launch-path)) and does not delay shell or explorer startup. The `+` tooltip stays “Open folder”.

The Grok row label is Grok Build. Its 16px leading slot paints the official mark in `crates/made-app/assets/grok.svg` (the two paths from https://grok.com/images/favicon.svg, fill #FCFCFC, viewBox "56 56 400 400"). While OpenCode is not active, a running Grok TUI — even before a session exists — or a shell tab with open Grok sessions shows that same `Grok Build` label and official mark in the workspace tab's 16px leading slot. The tooltip is the session summary when sessions exist and omits the workspace path. When that Grok is no longer running and the tab has no open Grok sessions, the tab returns to the folder label and the terminal glyph. OpenCode, when active, keeps its label, icon, and dots. OpenCode keeps `opencode.svg` and its launch injection; see [OpenCode bridge](opencode.md).

Choosing Grok starts the absolute `grok` path with the argument `dashboard` as the child of a new home-directory tab, with no shell first and no picker, and the current tab keeps running. Made does not inject the plugin into the Grok launch and does not hand-edit Grok `config.toml`. Grok honors `BROWSER`, so its URLs go to the ask-before-open card ([URL open requests](../runtime/terminal-first.md#url-open-requests)).

After PATH detection reports grok, Made runs the official install of the shipped `plugins/grok-made` with trust, on background work that does not block startup. The installed copy lives under `$GROK_HOME/installed-plugins/` (default `~/.grok`). An explicit catalog without detection does not install. The shipped package carries the native hook `made-grok-status` (`made-grok-status.exe` on Windows) for the host target, built from [`crates/made-grok-hook`](../../crates/made-grok-hook); no Python or other interpreter is a prerequisite. Install failure still lets Grok start, and Made records that session-status hooks are unavailable. Uninstall remains `grok plugin uninstall grok-made --confirm`, and Made does not run it.

Made and the native hook resolve the Grok home with one rule: a non-empty `GROK_HOME`, else `std::env::home_dir()` joined with `.grok` (`USERPROFILE` on Windows). Never look up `HOME` alone: Windows GUI launches have no `HOME`, which silently breaks install detection and session follow. The single resolver is `grok_home_dir()` in [`plugin.rs`](../../crates/made-app/src/integrations/grok/plugin.rs), shared by the install check, the status log, and the session inventory.

The session-follow contract is [`spec.md`](../../specs/grok-session-follow.md). Revealed About diagnostics show one Grok Build status row only after “Show diagnostics”, next to the OpenCode status pill and not in the workspace chrome; outcomes are checking, not on PATH, installing, hooks unavailable, and an explicit catalog that did not detect does not install. The ready outcome appears only while that workspace's Grok process is still alive or its shell has an open Grok session; when the plugin is installed and Grok is not running there, the row stays inactive. Focusing an already-open Grok session does not move the explorer.

## SSH workspaces

For a registered SSH server, the `+` flow offers `Terminal SSH`, plus `OpenCode SSH`, `Grok SSH` and `Claude Code SSH` when that server's bounded remote `PATH` lookup detects each program. `Grok SSH` starts the detected remote `grok` with the single `dashboard` argument directly in a tab bound to that server and remote directory, with no shell first and no injected plugin configuration; typing `grok` in a remote shell remains the manual path and gets no `dashboard` argument. The remote surface reuses the local presentation: exact `Grok Build` label and mark, session dots, newest-session explorer follow, tooltip, diagnostics row, the shared root and presentation order (OpenCode, then [Claude Code](claude-code.md#ssh), then Grok, as locally), and the server-name label when Grok is no longer running and no session remains, all from the owning tab's remote state. The contract is [`specs/ssh-remote-workspaces.md`](../../specs/ssh-remote-workspaces.md); SSH-10 is the Grok part.

For session follow, the server-side companion reads only two Grok-native state files under the remote `$GROK_HOME` (`~/.grok` when unset): `active_sessions.json` about once a second, and appended lines from `made-grok-status.jsonl`. The inventory tier needs no plugin, consent, or remote write; owned sessions appear from live process ancestry, and sessions seen only there show idle. Hook activity requires an installed `grok-made` equal to or newer than the shipped package version (the workspace version, 0.1.0 at the first release); there is no `python3` requirement and no python3-missing state, and otherwise the tab stays on inventory with session-status hooks reported unavailable. A user-installed equal/newer plugin supplies hooks without Made consent because Made writes nothing, while Made's official installer needs its own per-server/version consent after companion staging. The shipped native hook records the Grok parent pid, so owned events apply immediately and unproven events do not cross tabs even though the hook log is server-global.

The remote stage set is 14 artifacts: `made-remote`, five OpenCode plugin files, the Grok `plugin.json`, `README.md`, `hooks/hooks.json` and `hooks/bin/made-grok-status`, and the Claude Code `.claude-plugin/plugin.json`, `README.md`, `hooks/hooks.json` and native `made-claude-status` hook (added in v0.1.2 by [`ssh-claude-code-parity`](../../specs/changes/archive/20261126-ssh-claude-code-parity/proposal.md)); both hooks are built under the same glibc 2.31 / macOS 12 floors as `made-remote`. See [ADR 0006](../decisions/0006-native-grok-hook.md).

Host-companion parity covers 16 Grok scenarios plus 15 intended-failure controls over a real loopback `sshd`; debug and release workspace test gates pass, and teardown leaves no companion or supervisor processes. The live plantsuite/native GUI matrix remains pending, so no external-server validation is claimed.
